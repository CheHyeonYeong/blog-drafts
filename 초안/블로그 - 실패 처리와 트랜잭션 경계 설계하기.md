# 실패 처리와 트랜잭션 경계 설계하기

> 티스토리 초안 · 2026-10-26
> 출발점: [[2026-10-15]], [[커리어/다양한학습자를위한/ice-clinic/에러 컨벤션/에러 규칙|에러 규칙]]
> 실제 프로젝트에서 검토한 판단 기준을 별도의 SQLite 예제로 재구성했다. 아래 상황은 기존 서비스에서 발생한 장애를 재현한 것이 아니다.
> 확인 환경: Node.js v24.22.1, 내장 SQLite 3.53.4. 본문의 네 사례를 메모리 DB에서 실행해 표의 행 수를 확인했다.

함수의 실패를 다루는 방법에는 여러 가지가 있다. 실패 코드를 반환할 수도 있고, 예외를 던져 호출자가 잡게 할 수도 있다. 사용자에게 같은 오류 메시지를 보여줄 수 있어서 처음에는 코드 스타일의 차이처럼 느껴진다.

그런데 함수 안에서 데이터를 저장하면 다른 질문이 생긴다. 실패하기 전에 실행한 쓰기는 취소해야 할까, 남겨야 할까?

검사 결과를 저장하다 필수 조건을 만족하지 못했다면 저장을 막아야 한다. 반면 로그인 인증번호가 틀렸다면 실패 시도는 기록해야 한다. 사용자에게는 둘 다 실패지만 DB에 남아야 할 결과는 다르다. 에러 처리 규칙을 정리하면서 이 차이를 먼저 설명할 필요가 있었다.

## 실패 응답과 저장 결과는 별개의 결정이다

상품을 등록하면서 초기 재고도 저장하는 작업을 생각해 보자. 두 저장이 함께 성공해야 한다면 하나의 트랜잭션으로 묶는다. 트랜잭션은 커밋으로 변경을 확정하거나 롤백으로 변경을 취소하는 단위다. [PostgreSQL 트랜잭션 설명](https://www.postgresql.org/docs/current/tutorial-transactions.html)

여기서 JavaScript의 `return { ok: false }`가 DB의 `ROLLBACK`을 의미하지는 않는다. DB는 그 객체의 업무적 의미를 알지 못한다. 트랜잭션을 감싼 라이브러리나 코드가 반환과 예외를 어떤 SQL로 연결하는지가 중요하다.

Drizzle도 트랜잭션 콜백과 명시적인 `tx.rollback()` API를 제공한다. 실제로 사용하는 드라이버에 맞춰 그 계약을 확인해야 한다. 아래에서는 ORM 내부를 추측하는 대신, 아주 작은 동기식 래퍼를 작성해 제어 흐름을 드러내 보겠다. [Drizzle 트랜잭션 API](https://orm.drizzle.team/docs/transactions)

## 커밋과 롤백을 직접 연결해 보기

Node.js의 `node:sqlite`를 이용하면 외부 DB 서버 없이 메모리 DB에서 비교할 수 있다. 다음 코드를 `transaction-demo.mjs`에 저장한다. 이어지는 네 사례도 같은 파일에 순서대로 붙여 `node transaction-demo.mjs`로 실행한다.

```js
import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync(":memory:");
db.exec("CREATE TABLE records (id INTEGER PRIMARY KEY, label TEXT NOT NULL)");

const insert = db.prepare("INSERT INTO records (label) VALUES (?)");
const count = db.prepare("SELECT COUNT(*) AS n FROM records");

class Rejected extends Error {}

// 동기식 콜백만 사용한다. 중첩·비동기 작업용 범용 래퍼가 아니다.
function transactionSync(work) {
  db.exec("BEGIN");
  try {
    const result = work();
    db.exec("COMMIT");
    return result;
  } catch (error) {
    db.exec("ROLLBACK");
    throw error;
  }
}

function reset() {
  db.exec("DELETE FROM records");
}

function printCount(label) {
  console.log(`${label}: ${count.get().n}`);
}
```

`work()`가 정상 반환하면 `COMMIT`을 실행한다. 예외가 래퍼의 `catch`까지 올라오면 `ROLLBACK`을 실행한다. 이 예제에서 DB 결과를 결정하는 지점은 바로 이 두 갈래다.

`DatabaseSync`는 동기 API이므로 예제에 `async` 콜백을 넘기지 않는다. 실무용 래퍼에는 잘못된 콜백 사용, 중첩 트랜잭션, 롤백 자체의 오류 처리 같은 고려가 더 필요하다. 여기서는 반환과 예외의 차이를 관찰하는 범위로 제한한다. [Node.js SQLite API](https://nodejs.org/api/sqlite.html)

## 실패를 반환하면 앞선 쓰기는 남는다

먼저 레코드를 저장한 다음 실패 객체를 반환해 보자.

```js
reset();
const returned = transactionSync(() => {
  insert.run("첫 번째 기록");
  return { ok: false, code: "rejected" };
});

console.log("반환 결과:", returned.ok);
printCount("실패 반환 후 행 수");
```

결과 객체의 `ok`는 `false`지만 행 수는 `1`이다. 콜백은 정상적으로 반환됐고, 래퍼는 반환 객체를 해석하지 않은 채 커밋했다.

이 흐름 자체가 버그인 것은 아니다. 실패 횟수를 남기는 작업이라면 원하는 동작일 수 있다. 반대로 먼저 저장한 기록도 취소해야 하는 작업이라면 반환만으로는 요구를 충족하지 못한다.

## 예외가 트랜잭션 밖으로 전달되면 취소된다

같은 위치에서 예외를 던지면 결과가 달라진다.

```js
reset();
try {
  transactionSync(() => {
    insert.run("첫 번째 기록");
    throw new Rejected("두 번째 작업을 진행할 수 없습니다");
  });
} catch (error) {
  if (!(error instanceof Rejected)) throw error;
  console.log("거절 사유:", error.message);
}

printCount("예외 전파 후 행 수");
```

이번에는 행 수가 `0`이다. 예외가 트랜잭션 래퍼에 도달해 롤백이 실행됐고, 바깥의 `catch`가 사용자에게 전달할 거절 사유를 처리했다.

커스텀 클래스 `Rejected`가 특별한 롤백 능력을 갖는 것은 아니다. 이 예제에서는 일반 `Error`를 던져도 래퍼가 똑같이 처리한다. 클래스는 바깥 호출자가 자신이 처리할 실패를 식별하도록 사용했다. 다른 오류까지 같은 거절 사유로 바꾸지 않도록, 여기서는 나머지 오류를 다시 던진다.

## catch의 위치가 달라지면 저장 결과도 달라진다

예외를 던졌다는 사실만 확인하면 다음 코드를 놓치기 쉽다.

```js
reset();
transactionSync(() => {
  insert.run("첫 번째 기록");

  try {
    throw new Rejected("두 번째 작업을 진행할 수 없습니다");
  } catch (error) {
    if (!(error instanceof Rejected)) throw error;
    return { ok: false, code: "rejected" };
  }
});

printCount("안에서 잡은 후 행 수");
```

행 수는 다시 `1`이다. 콜백 안에서 예외를 잡고 정상 반환했으므로 래퍼의 `catch`는 실행되지 않았다. 같은 메시지와 같은 에러 클래스를 사용해도 예외가 어디까지 전달되는지에 따라 결과가 달라진다.

이 사례는 직접 던진 애플리케이션 예외를 비교한 것이다. 실제 SQL 문장이 실패하면 DBMS에 따라 트랜잭션이 실패 상태가 되는 등 추가 동작이 있다. 따라서 모든 DB 오류를 안에서 잡으면 커밋할 수 있다는 의미로 일반화하면 안 된다.

## 커밋한 뒤의 예외는 이미 끝난 트랜잭션을 되돌리지 않는다

반대 방향으로도 경계를 확인할 수 있다.

```js
reset();
try {
  transactionSync(() => {
    insert.run("첫 번째 기록");
  });

  throw new Rejected("응답을 만들던 중 거절했습니다");
} catch (error) {
  if (!(error instanceof Rejected)) throw error;
  console.log("응답 실패:", error.message);
}

printCount("커밋 뒤 예외 발생 시 행 수");
db.close();
```

행 수는 `1`이다. `transactionSync()`가 반환한 시점에는 이미 커밋을 마쳤다. 그다음 실행한 코드의 예외가 과거의 커밋을 취소하지는 않는다.

네 사례에서 확인할 값은 다음과 같다.

| 콜백과 호출자의 동작 | 남는 행 수 | 이 예제의 이유 |
| --- | ---: | --- |
| 저장 후 실패 객체 반환 | 1 | 콜백 정상 반환 → 커밋 |
| 저장 후 예외를 바깥으로 전파 | 0 | 래퍼에서 예외 포착 → 롤백 |
| 저장 후 콜백 안에서 예외를 잡고 반환 | 1 | 래퍼에는 정상 반환으로 보임 |
| 콜백 정상 종료 후 바깥에서 예외 발생 | 1 | 이미 커밋 완료 |

## 로그인 실패는 왜 저장해야 할까

이제 로그인 인증번호 검증에 적용해 보자. 잘못된 번호를 입력한 횟수를 기록하고 일정 횟수 이상이면 요청을 제한하려고 한다.

이 작업에서는 ‘인증 실패’가 기록을 취소할 이유가 되지 않는다. 오히려 그 실패가 저장하려는 사건이다. 흐름을 다음과 같이 정할 수 있다.

```text
트랜잭션 시작
  → 현재 시도 상태 확인
  → 인증번호 검증
  → 잘못된 번호라면 실패 시도 기록
  → { ok: false, code: "invalidCode" } 반환
트랜잭션 커밋
  → 웹 호출자가 사용자에게 실패 안내
```

이때 실패 시도를 저장한 다음 예외를 트랜잭션 밖으로 던지면, 롤백으로 그 시도 기록까지 사라질 수 있다. 사용자에게 실패를 알리는 것과 실패 사실을 영구 기록하는 것이 동시에 필요한 사례다.

반대로 상품과 초기 재고가 반드시 함께 있어야 한다면, 재고 저장에 실패했을 때 상품만 남으면 안 된다. 두 작업을 같은 트랜잭션에 넣고, 실패가 트랜잭션 취소로 이어지도록 해야 한다.

따라서 ‘예상 가능한 실패는 반환’이라는 규칙만으로는 부족하다. **그 실패 직전에 무엇을 썼고, 그 쓰기가 남아야 하는지**까지 결정해야 한다. 아직 쓰기 전이라면 실패를 반환해도 취소할 변경이 없다.

## 오류를 화면에 표시하는 책임

저장 결과를 정했다면 그다음은 호출자에게 어떻게 보여줄지다. SvelteKit의 remote form에서는 `invalid()`로 검증 문제를 전달할 수 있다. 이 함수는 예외를 던지는 방식으로 동작한다. [SvelteKit의 프로그램 검증](https://svelte.dev/docs/kit/remote-functions#form-Programmatic-validation)

트랜잭션을 마친 뒤 `invalid()`를 호출하면 폼에는 실패를 표시할 수 있지만, 앞에서 커밋한 기록은 남는다. 로그인 실패 기록에서는 이 동작이 필요할 수 있다. 앞선 쓰기를 취소해야 하는 작업이라면 웹 응답을 만들기 전에 트랜잭션 안에서 취소가 이뤄져야 한다.

웹과 CLI가 같은 저장 로직을 사용하는 경우에는 두 호출자가 같은 실패를 다르게 표현한다. 웹은 폼 메시지를 표시하고, CLI는 로그와 종료 코드로 전달할 수 있다. 공용 로직은 두 환경이 해석할 수 있는 결과나 오류를 전달하고, 각 호출자가 표시 방법을 정하면 된다.

파일 이름이 `server.ts`라는 이유만으로 모든 웹 헬퍼를 금지할 필요는 없다. 실제로 누가 호출하는지, HTTP 요청 밖에서도 사용하는지를 기준으로 의존성을 정하는 편이 구체적이다. 이 부분은 프로젝트의 호출 구조에 맞춘 설계 판단이다.

## 트랜잭션이 끝내 주지 않는 문제

반환과 예외를 올바르게 나눠도 동시 요청은 별도로 고려해야 한다. 두 요청이 같은 실패 횟수를 읽고 각각 1을 더해 저장하면 증가분을 잃을 수 있다. 원자적인 갱신, 잠금, 격리 수준 등에서 해당 업무 규칙을 지킬 방식을 선택해야 한다. 트랜잭션으로 묶었다는 사실만으로 모든 경쟁 조건이 없어지는 것은 아니다. [PostgreSQL 격리 수준](https://www.postgresql.org/docs/current/transaction-iso.html)

외부 시스템도 경계 밖에 있다. DB 트랜잭션 도중 보낸 이메일은 DB를 롤백한다고 회수되지 않는다. ‘신청 저장과 알림 요청을 함께 남긴 뒤 발송을 재시도한다’ 같은 구조를 고려하더라도, 중복 처리와 실패 복구는 그 구조에 맞춰 추가로 설계해야 한다.

드라이버의 실행 방식도 확인해야 한다. 앞의 래퍼는 동기 콜백의 종료를 기준으로 커밋한다. 비동기 콜백은 Promise를 반환하므로, 같은 코드를 그대로 적용하면 비동기 작업이 끝나기 전에 커밋할 수 있다. 실제 라이브러리가 콜백의 Promise를 기다리는지는 사용하는 어댑터의 계약으로 확인해야 한다. 이 글의 예제만으로 특정 ORM 전체에 async 콜백을 금지하는 결론을 내릴 수는 없다.

실패 처리를 읽을 때는 이제 `return`과 `throw`보다 먼저 저장 결과를 보게 된다. 작업이 거절됐을 때 무엇이 남아야 하는지 정하고, 커밋과 롤백의 경계가 그 요구를 만족하는지 확인한다. 같은 오류 메시지를 보여주는 코드라도 DB에 남는 결과까지 같지는 않기 때문이다.
