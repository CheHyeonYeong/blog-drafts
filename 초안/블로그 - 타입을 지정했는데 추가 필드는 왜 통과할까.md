# 타입스크립트야, 너 지금 누구 편이야?

*타입에 없는 필드 하나 쫓아내려다가 구조적 타이핑과 Valibot까지 간 이야기.*

TypeScript를 쓰는 이유가 뭘까.

적어도 나는 내가 이상한 짓을 하면 누군가 말려줬으면 했다. 런타임까지 가서 터지기 전에 편집기가 빨간 줄로 “그거 아닌데요” 해주는 삶. 좀 귀찮아도 그 편이 낫다고 생각했다.

그런데 `db.transaction<…>`을 쓰다가 이상한 걸 봤다. 결과로 쓸 타입을 지정했는데, 콜백에서 객체에 필드를 하나 더 넣어도 통과했다. 필요한 필드의 자료형을 틀리면 잡아준다. 필수 필드를 빼먹어도 잡아준다. 그런데 필요 없는 필드를 더 넣으면?

> 들어가세요.

아니 잠깐만요. 내가 명단까지 줬는데 왜 들여보내세요.

처음에는 내가 타입을 덜 적었나 싶었다. TypeScript가 말을 안 들으면 일단 타입을 더 적어보는 편이다. 개발 실력이 늘어서가 아니라, 아직 내가 할 수 있는 게 그것뿐인 경우가 꽤 있기 때문이다.

반환 타입을 적어봤다. `satisfies`도 붙여봤다. 제네릭에 `extends`까지 붙이면 뭔가 엄격해 보인다. 꺾쇠괄호가 늘어날수록 보안도 강해질 것 같은 기분이 든다. ~~기분만 그랬다.~~

결국 알아보려던 건 이것이다.

**타입에는 없는 필드인데, 왜 어떤 데서는 쫓겨나고 어떤 데서는 멀쩡히 들어가 있지?**

오늘의 실험 대상은 `debug: true`다. 딱히 잘못한 건 없지만 내가 내보내고 싶으니까 나가줬으면 한다. 그런데 이 친구, 생각보다 안 나간다.

아래 코드는 이 의문을 확인하려고 따로 만든 예제다. 실제 서비스에서 정보가 유출됐다는 이야기도 아니고, 특정 DB 라이브러리의 버그를 잡았다는 이야기도 아니다. 그 정도로 큰 사건인 줄 알았는데 내 타입 이해도가 사건이었다.

## 1. 타입에 없는데요? — 네, 객체에는 있습니다

일단 응답에 필요한 것은 `id` 하나라고 하자. 글도 길어질 예정인데 필드까지 많으면 나부터 도망갈 것 같아서 하나만 둔다.

```ts
type Reply = {
  id: string;
};

const source = {
  id: "p1",
  debug: true,
};

const reply: Reply = source;

console.log(reply.id); // p1
// @ts-expect-error: Reply에는 debug가 선언되어 있지 않다
console.log(reply.debug); // 실행하면 true
console.log(reply === source); // true
```

여기서 벌써 마음에 안 드는 일이 두 개 생긴다.

첫째, `source`에는 `debug`가 있는데 `Reply`에 대입이 된다. 둘째, 그렇게 대입해 놓고 `reply.debug`를 읽으려고 하면 빨간 줄이 뜬다.

> 넣을 때는 괜찮다며.
> 왜 꺼낼 때는 모르는 척해?

이 상황을 이해하려면 화면에 보이는 타입과 실제 객체를 잠깐 나눠야 한다. `source`의 타입에는 `id`와 `debug`가 모두 잡혀 있다. `reply`는 내가 `Reply`라고 선언했으므로, 그 변수를 통해 사용할 수 있다고 알려진 속성은 `id`다.

그런데 `const reply: Reply = source`에는 객체를 새로 만들거나 속성을 삭제하는 코드가 없다. 같은 객체를 다른 변수로 보고 있을 뿐이다. 마지막 줄의 `reply === source`가 `true`인 이유다.

**내가 가린 것은 `debug`의 타입 정보였지, `debug` 자체가 아니었다.**

마치 폴더를 숨김 처리해 놓고 파일을 삭제했다고 생각한 셈이다. 안 보이기는 한다. 용량은 그대로다. 여기서도 자동완성에서는 안 보이는데 객체에는 그대로 있다.

`@ts-expect-error`는 바로 다음 줄에서 타입 오류가 나야 한다는 검증 표시다. 글에서는 오류가 필요한 예제에 붙였다. 주석을 지우면 실제 진단을 볼 수 있다. “오류를 없애는 꿀팁”으로 쓰면 안 된다. 오늘 오류를 피하는 방법만 배우면 나는 2만 자짜리 삽질 장려문을 쓴 사람이 된다.

또한 코드 블록은 각각 별도 파일로 읽으면 된다. 오류를 표시한 코드도 출력해서 실행하면 첫 예제의 `reply.debug`는 `true`다. 오류가 있는 코드를 배포하자는 뜻은 아니고, 타입 오류와 실제 실행 결과가 무엇이 다른지 관찰하기 위한 실험이다.

## 2. 나는 출입 명단을 줬는데, TypeScript는 자격 요건으로 읽었다

나는 `type Reply = { id: string }`을 대충 이렇게 읽고 있었다.

> 이 객체에는 `id`만 있어야 함. 다른 놈은 출입 금지.

그런데 평범한 객체의 구조적 호환성을 검사하는 상황에서 TypeScript가 보는 것은 이쪽에 가깝다.

> 문자열 `id`가 필요함. 가지고 계신가요?

명단이 아니라 자격 요건이었다. `debug`가 같이 왔다고 `id`가 갑자기 숫자가 되는 것은 아니다.

```ts
type Reply = { id: string };

function printId(value: Reply): void {
  console.log(value.id);
}

const fromDatabase = {
  id: "p1",
  createdAt: "2026-10-29",
  internalNote: "example",
};

printId(fromDatabase); // 통과
```

`printId`는 문자열 `id`만 읽는다. `fromDatabase`에는 그게 있다. 생성 시각이나 내부 메모가 더 있어도 `value.id`를 읽는 데 필요한 조건은 충족한다. 그래서 전달할 수 있다. 이것이 이 예제에서 보는 구조적 타이핑이다. [TypeScript의 타입 호환성](https://www.typescriptlang.org/docs/handbook/type-compatibility.html)

이게 왜 이렇게 생겼을까 싶지만, 사용하는 쪽으로 생각하면 꽤 편하다. DB에서 열 개의 속성을 가져왔는데 `id`만 출력하는 함수가 있다고 하자. 그 함수를 부를 때마다 “잠깐, 다른 아홉 개를 버린 전용 객체를 만들어야 합니다” 하면 그것도 피곤하다.

필요한 부분만 요구하는 함수에 더 많은 정보를 가진 값을 넘길 수 있다. TypeScript가 나를 배신한 것이 아니라, 평소에는 내가 잘 써먹던 규칙이 마음에 안 드는 자리에서 등장한 것이다. ~~선택적 구조적 타이핑 지지자.~~

그렇다고 아무 객체나 받아준다는 뜻은 아니다.

```ts
type Reply = { id: string };

const wrongType = { id: 123, debug: true };
const missingId = { debug: true };

// @ts-expect-error: id는 string이어야 한다
const a: Reply = wrongType;

// @ts-expect-error: 필수 속성 id가 없다
const b: Reply = missingId;
```

`id`가 숫자이거나 아예 없으면 안 된다. 변수에 한 번 넣었다고 이 조건까지 사라지지는 않는다. 이 두 오류는 “추가 필드가 있다”와 다른 문제다.

여기서부터는 질문을 정확하게 해야 한다. 내가 궁금한 것은 TypeScript가 타입 검사를 하는지 아닌지가 아니다. **필요한 필드가 있는 것을 검사하는지, 불필요한 필드가 없는 것까지 검사하는지**다.

일단 우리가 보고 있는 것은 `id: string`을 가진 보통의 객체다. 함수 매개변수, 클래스의 private/protected 멤버, 유니언 같은 곳까지 “필요한 것만 있으면 무조건 OK”로 밀어붙이지는 말자. 하나 이해했다고 타입 시스템 전체를 정복한 기분이 들 때가 제일 위험하다. 보통 다음 코드 블록에서 바로 혼난다.

## 3. 변수 한 번 거쳤더니 입장 가능? 얘 인맥 있나?

그런데 앞의 설명을 듣고 다음 코드를 보면 다시 어이가 없어진다.

```ts
type Reply = { id: string };

// @ts-expect-error: 객체 리터럴에 직접 작성한 추가 속성
const direct: Reply = { id: "p1", debug: true };

const source = { id: "p1", debug: true };
const indirect: Reply = source; // 통과
```

위쪽은 오류다. 아래쪽은 통과다.

값에 들어 있는 것은 똑같다. `id: "p1"`, `debug: true`. 그런데 `source`라는 변수에 한 번 들렀더니 대우가 달라졌다. 변수 이름이 추천서라도 써준 건가?

여기서 등장하는 것이 **초과 속성 검사(excess property checking)**다. 새 객체 리터럴을 특정 타입에 맞춰 직접 작성하는 자리에서는, 알 수 없는 속성을 추가로 확인한다. `direct`의 대입이 그 자리다. [초과 속성 검사 문서](https://www.typescriptlang.org/docs/handbook/2/objects.html#excess-property-checks)

왜 굳이 한 번 더 보느냐고 하면, 객체를 직접 쓰는 사람은 오타도 직접 쓰기 때문이다. 설정에 `timeout`을 넣으려다 `timeuot`이라고 적었는데 “추가 정보가 많으시네요. 통과” 하면 곤란하다. 컴파일러가 이 자리에서는 작성 실수의 냄새를 조금 더 맡는 셈이다.

반면 `indirect`는 이미 타입이 추론된 변수의 값을 받는다. 여기서는 `source`가 `Reply`로 쓰일 수 있는지 본다. 앞에서 봤듯 필요한 `id`가 있으니 호환된다.

따라서 “변수로 빼면 타입 검사를 우회할 수 있다”로 끝내면 반만 이해한 것이다. 필수 속성과 값의 타입은 여전히 검사한다. 새 리터럴에 붙던 초과 속성 검사가 같은 방식으로 적용되지 않는 것이다.

이 현상을 설명할 때 *fresh object literal*이라는 표현도 나온다. fresh라고 해서 생성 후 3초 이내의 신선한 객체를 뜻하지는 않는다. ~~냉장 보관하면 freshness가 유지되는 것도 아니다.~~ 컴파일러가 표현식을 다루는 방식과 관련된 말이다.

지금은 용어보다 작성 위치를 보면 된다. 새 리터럴을 목표 타입에 직접 맞추는가? 이미 있는 변수의 호환성을 확인하는가? 두 자리에 같은 모양의 객체가 등장했다고 같은 검사가 실행되는 것은 아니다.

그런데 여기서 “아하, 변수에 넣으면 추가 필드는 다 통과!”라고 외우면 바로 다음 함정이 있다. 친절하게 하나씩 나오는 편이다.

## 4. 오타도 외로우면 잡힌다

이번에는 모든 속성이 optional인 설정 객체다.

```ts
type Options = {
  timeout?: number;
  retries?: number;
};

function configure(options: Options): void {
  console.log(options);
}

// @ts-expect-error: timeout을 잘못 적었다
configure({ timeuot: 1000 });

const typoOnly = { timeuot: 1000 };
// @ts-expect-error: Options와 공통 속성도 없는 객체다
configure(typoOnly);

const mixed = { timeout: 1000, timeuot: 2000 };
configure(mixed); // 통과
```

`typoOnly`는 분명 변수인데 오류가 난다. 앞에서 변수 하나면 통과라고 하지 않았냐고 묻고 싶지만, 나는 정확히는 그렇게 말하지 않았다. ~~이래서 문장이 길어지나 보다.~~

이 예제의 `Options`는 모든 속성이 optional이다. 여기에 공통 속성이 전혀 없는 객체를 전달하면 오류가 발생하는 경우가 있다. `typoOnly`에는 틀린 `timeuot`만 있고, `Options`가 아는 속성은 하나도 없다.

그런데 `mixed`는 진짜 `timeout`도 가지고 있다. 필요한 공통점이 생겼고, 추가된 `timeuot`은 함께 통과한다. 잘 쓴 필드 하나 옆에서 오타가 조용히 살아남았다.

그래서 에러 메시지를 읽어야 한다. 빨간 줄은 하나의 감정 표현이 아니다. 필드가 없다는 건지, 값이 틀렸다는 건지, 알 수 없는 키라는 건지, 공통 속성이 없다는 건지가 다르다. “어떻게 하면 빨간 줄이 없어지지?”만 생각하면 그 검사들이 전부 귀찮음 하나로 합쳐진다.

여기서 `[key: string]: unknown`을 추가하면 임의의 문자열 키를 열어둘 수 있다. 하지만 그건 타입을 수리한 것이 아니라 계약을 바꾼 것이다. 정말 아무 키나 받아도 되는 설정이라면 괜찮다. 정해진 옵션만 받아야 하는데 오류가 싫어서 문을 열었다면, 이제 오타도 정식 손님이다.

내가 원하는 것이 설정 확장인지 오타 검출인지 먼저 정해야 한다. 문이 안 열린다고 문짝을 떼면 출입 문제는 해결된다. 보통 그걸 수리라고 하지는 않는다.

## 5. 반환 타입까지 적었는데 또 너야?

이번에는 함수다. 반환 타입을 명시하면 좀 확실해 보인다. 함수가 나가는 길에 `: Reply`라고 크게 붙였으니 이제 `debug`는 못 나올 것 같다.

```ts
type Reply = { id: string };

function makeDirect(): Reply {
  // @ts-expect-error: 반환 타입에 없는 속성을 직접 작성했다
  return { id: "p1", debug: true };
}

function makeThroughVariable(): Reply {
  const source = { id: "p1", debug: true };
  return source; // 통과
}
```

첫 번째 함수는 예상대로 오류가 난다. 그래서 잠깐 기분이 좋아진다.

두 번째 함수는 통과한다. 기분이 끝났다.

다시 보면 처음 대입 예제와 똑같다. `makeDirect`는 `Reply`를 반환하는 자리에서 새 리터럴을 직접 반환한다. `makeThroughVariable`은 이미 만들어 둔 변수의 값을 반환한다. 함수로 감쌌지만 앞에서 보던 차이가 사라진 것은 아니다.

`function makeThroughVariable(): Reply`는 호출자에게 `Reply`를 반환하겠다는 정적 계약이다. 호출자는 `id`가 문자열이라고 알고 쓸 수 있다. 내부 구현에 `debug`가 있다는 정보까지 공개된 타입에 포함하지 않는다.

하지만 반환 타입을 썼다고 `return source`가 자동으로 `return { id: source.id }`로 바뀌지는 않는다. 코드는 내가 쓴 대로 실행된다. 나는 `source`를 반환하라고 했다. 컴파일러는 시키지도 않은 청소를 해주지 않는다.

반환 타입이 쓸모없다는 결론도 아니다. 필수 필드를 빠뜨리거나 잘못된 자료형을 반환하는 실수를 함수 경계에서 발견하는 데 도움이 된다. 다만 거기에 추가 속성 삭제 서비스까지 포함되어 있다고 생각하면 안 된다. ~~타입스크립트 프리미엄을 결제해도 그런 서비스는 없다.~~

비동기 함수에 `Promise<Reply>`를 적어도 실제 객체를 구분해야 한다는 원칙은 같다. `await`를 통과한다고 불필요한 필드가 증발하지 않는다. 비동기는 세탁기가 아니다.

## 6. 콜론을 어디에 썼느냐고요? 그게 그렇게 중요해요?

중요했다.

```ts
type Reply = { id: string };

const inferredFunction: () => Reply = () => ({
  id: "p1",
  debug: true,
}); // 통과

const explicitReturn = (): Reply => ({
  id: "p1",
  // @ts-expect-error: 반환 타입을 명시한 리터럴의 추가 속성
  debug: true,
});
```

처음 이 둘을 보면 둘 다 `Reply`를 반환하는 함수라고 적어둔 것 같다. 나도 이 정도면 같은 의사 표현이라고 주장하고 싶다. 그런데 컴파일러는 인간관계처럼 대충 의도를 봐주지 않는다. 위치를 본다.

첫 번째의 `: () => Reply`는 **변수에 붙인 함수 타입**이다. 오른쪽 함수를 `Reply`를 반환하는 함수로 쓸 수 있는지 확인한다. 더 많은 속성을 반환하더라도 호출자는 `id`를 읽을 수 있으므로 이 예제는 통과한다.

두 번째의 `(): Reply =>`는 **화살표 함수 자체에 적은 반환 타입**이다. 그 반환 위치에서 직접 만든 리터럴을 검사한다. `debug`가 초과 속성으로 걸린다. [함수 타입 표현식과 반환 타입](https://www.typescriptlang.org/docs/handbook/2/functions.html)

사용하는 쪽의 기대를 생각해 보면 첫 번째가 통과하는 이유도 납득할 수 있다. “문자열 `id`가 있는 값을 돌려줄 함수 주세요”라고 했는데, `id`와 `debug`를 돌려주는 함수가 왔다. `id`를 읽는 데는 지장이 없다. 돌려주는 값에 추가 정보가 있을 뿐이다.

여기서 매개변수까지 똑같은 방향으로 판단하면 안 된다. 함수 타입의 호환성은 반환값과 매개변수를 구분해 생각해야 한다. 지금 실험은 반환 객체의 추가 속성에 대한 것이다. 모든 함수 타입 이론을 이 문단 하나로 해결하려고 하면 글이 아니라 입학 안내서가 된다.

중요한 건 이제 `Reply`라는 단어만 찾지 않게 됐다는 것이다. 같은 타입 이름이 있어도 변수의 타입인지, 함수의 반환 타입인지, 콜백을 받는 쪽의 타입인지 봐야 한다.

나는 “타입 다 적었는데 왜 이러지?”라고 했지만, 컴파일러 입장에서는 어디에 적었는지를 끝까지 읽어야 하는 상황이었다. 계약서를 썼다는 사실과 계약서에 무엇을 썼는지는 다르다. 개발하면서 계약서 읽기까지 해야 한다니 인생 쉽지 않다.

## 7. 제네릭을 범인으로 잡았는데 알리바이가 있다

처음에는 꺾쇠괄호를 의심했다. 현장에 `<Reply>`가 있었으니까.

그런데 `<T>`는 “반환 타입”이라는 뜻의 문법이 아니다. 타입 매개변수다. 무엇을 연결하는지는 함수 선언을 봐야 한다. 이걸 대충 “제네릭에 반환 타입을 적었는데요”로 줄이면 설명에서 범인과 목격자가 바뀐다.

```ts
type Reply = { id: string };

function run<T>(work: () => T): T {
  return work();
}

const result = run<Reply>(() => ({ id: "p1", debug: true }));

// @ts-expect-error: id의 자료형은 여전히 검사한다
run<Reply>(() => ({ id: 123 }));

// @ts-expect-error: id가 없는 반환값도 허용되지 않는다
run<Reply>(() => ({ debug: true }));
```

이 함수에서 `T`는 두 곳에 나온다. 콜백 `work`의 반환 타입과 `run` 자체의 반환 타입이다. 그래서 `run<Reply>`는 이 두 위치에 `Reply`를 사용한다. 꺾쇠괄호가 반환 타입 전용 문법이라서가 아니라, 내가 만든 시그니처가 두 자리를 연결하기 때문이다. [제네릭의 타입 매개변수](https://www.typescriptlang.org/docs/handbook/2/generics.html)

첫 호출은 통과하고, 숫자 `id`와 필드 누락은 오류가 난다. 그러니 타입 검사가 휴가 간 것도 아니다. 추가 필드가 있다는 사실만으로 이 콜백을 거부하지 않는 것이다.

이제 제네릭을 아예 빼보자. 억울한 용의자라면 풀어줘야 한다.

```ts
type Reply = { id: string };

function runReply(work: () => Reply): Reply {
  return work();
}

const result = runReply(() => ({ id: "p1", debug: true }));
console.log(JSON.stringify(result)); // {"id":"p1","debug":true}
```

똑같이 통과한다. 출력에도 `debug`가 있다.

제네릭이 없는데 현상이 그대로다. 그러면 “제네릭이 추가 필드를 놓친다”는 설명으로는 핵심을 못 잡는다. 우리가 보고 있는 것은 `() => Reply`에 맞는 함수를 받는 과정과, 함수의 반환 위치에서 직접 리터럴을 검사하는 과정의 차이다.

실제 `db.transaction`은 여기에 비동기 반환이나 오버로드, 트랜잭션 객체 타입 등이 더해질 수 있다. 따라서 이 작은 `run`으로 모든 라이브러리를 설명했다고 주장하지는 않는다. 업무 코드에서는 사용하는 버전의 선언으로 이동해 타입 인자가 어느 자리에 쓰이는지 봐야 한다.

그래도 라이브러리 이름을 지워보는 과정은 도움이 됐다. DB를 껐는데도 생기는 일이면 DB 탓을 하기 전에 멈출 수 있다. 매번 최종 보스부터 의심하면 내 코드 앞의 슬라임은 평생 못 잡는다.

## 8. extends까지 붙이면 좀 무서워 보이지 않을까?

추가 필드를 막고 싶어서 타입 문법을 더 가져오면 이런 코드도 생각할 수 있다.

```ts
type Reply = { id: string };

function keep<T extends Reply>(value: T): T {
  return value;
}

const kept = keep({ id: "p1", debug: true });
console.log(kept.debug); // true
```

안 무서워했다. `debug`가 아주 편하게 들어와 있다.

`T extends Reply`는 `T`가 `Reply`의 조건을 만족해야 한다는 제약이다. `T`가 가진 키가 `Reply`와 완전히 같아야 한다는 조건은 아니다. 이 호출에서 `T`는 `id`와 `debug`를 모두 가진 타입으로 추론될 수 있다. 그 타입은 문자열 `id`를 제공하므로 제약을 만족한다.

그리고 반환 타입도 `T`다. 덕분에 추가 정보가 보존된다. 이 함수는 “최소한 id는 있어야 하고, 나머지는 네가 가지고 온 대로 돌려줄게”라는 용도로는 잘 동작한다. 내가 쫓아내려고 부른 사람이 오히려 보관 서비스를 해주고 있었다.

타입 인자를 직접 `Reply`로 고정하는 호출과, `Reply`라는 제약 아래에서 더 구체적인 타입을 추론하는 호출은 다르다. 따라서 제네릭이 보이면 추가 필드는 무조건 통과한다거나, `extends`가 있으면 무조건 엄격해진다는 식으로 기억하지 않는다.

여기까지 오면 “TypeScript를 더 세게 써야 하나?”라는 질문이 조금 이상해진다. 세기의 문제가 아니라 계약의 문제다. 추가 정보를 보존하고 싶다는 계약과 추가 정보를 거부하고 싶다는 계약은 다르다. 내가 요청한 것은 전자인데 마음속으로 후자를 기대하고 있었다.

## 9. as, satisfies, 콜론. 셋 다 타입 붙이는 거 아니었어?

이쯤 되면 문법을 바꿔 끼워보고 싶어진다. 같은 `Reply`를 적을 방법이 여러 개면 하나쯤은 내가 원하는 일을 해주지 않을까. 개발자가 문제를 이해하기 직전에 자주 시도하는 가챠다.

```ts
type Reply = { id: string };

const source = { id: "p1", debug: true };

const annotated: Reply = source;
const asserted = source as Reply;
const checked = source satisfies Reply;

// @ts-expect-error: annotated는 Reply로 선언했다
annotated.debug;
// @ts-expect-error: asserted 표현식은 Reply로 단언했다
asserted.debug;
checked.debug; // 통과
```

세 줄 모두 통과한다. 그런데 `debug`를 읽을 수 있는 것은 `checked`다.

`: Reply`는 변수에 사용할 타입을 선언한다. 값이 그 타입과 호환되는지도 검사한다. 그래서 `annotated`를 통해 보는 타입은 `Reply`다.

`as Reply`는 그 표현식을 `Reply`로 취급하도록 단언한다. 단언도 허용 범위가 있지만, 런타임에서 객체를 검사하거나 바꾸는 명령은 아니다. `asserted`에서 `debug` 타입 정보가 안 보인다고 실제 속성까지 사라진 것은 아니다.

`satisfies Reply`는 표현식이 목표 타입에 맞는지 확인한다. 이 기존 변수 예제에서는 `source`의 구체적인 정보가 유지되어 `checked.debug`도 읽을 수 있다. [satisfies 설명](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator)

여기서 `as`로 빨간 줄을 없애는 것은 쉬워 보인다. 하지만 작성한 객체의 오타를 잡고 싶던 상황이라면, 오류를 없앴다는 사실 자체가 성과는 아니다. 화재경보기가 시끄럽다고 배터리를 뺐는데 집이 조용해졌다고 만족하면 안 된다.

물론 타입 단언이 필요한 경우도 있다. 실제로 값에 대해 컴파일러보다 더 많은 정보를 가지고 있을 수 있다. 다만 “나는 이 값의 타입을 안다”와 “왜 틀렸는지 모르겠는데 일단 통과하고 싶다”를 같은 `as`로 표현할 수 있다는 것이 문제다. 문법은 둘을 구분해 대신 양심 검사를 해주지 않는다.

`satisfies`도 과하게 신격화하면 안 된다. 목표 타입이 리터럴의 문맥적 추론에 관여할 수 있으므로 “추론에는 어떤 영향도 없다”라고 외우는 건 피한다. 이 예제에서 확인한 것은 기존 변수에 붙였을 때 `debug` 정보가 남는다는 것이다. ~~등장인물이 늘어날수록 각자의 약관도 늘어난다.~~

## 10. satisfies 붙였는데 왜 만족하냐고. 나는 불만족인데

이름부터 수상하다. 나는 불필요한 필드를 잡아달라고 붙였는데 컴파일러는 만족한다.

```ts
type Reply = { id: string };

// @ts-expect-error: 생성 지점의 추가 속성
const direct = { id: "p1", debug: true } satisfies Reply;

const source = { id: "p1", debug: true };
const indirect = source satisfies Reply; // 통과

console.log(indirect.debug); // true
```

첫 줄은 오류다. `indirect`는 통과한다. 이제 익숙한 패턴이다. 새 객체 리터럴을 만드는 자리와 기존 변수를 확인하는 자리의 차이가 또 나왔다.

`satisfies`는 “추가 키를 모조리 찾아내는 특별 수사반”이 아니다. `source`가 `Reply`와 호환되는지 물었고, 호환되니 통과했다. 나는 ‘만족한다’는 단어에 내가 원하는 조건을 전부 집어넣고 있었지만, 조건은 타입에 적힌 대로 해석된다.

새 객체를 만들면서 잘못된 필드를 잡고 싶다면 그 생성 지점에 `satisfies`를 놓는 것이 직접적이다. 반대로 이미 여러 함수를 거쳐 얻은 변수에 마지막으로 붙이면, 리터럴을 직접 작성할 때와 같은 초과 속성 검사를 기대하기 어렵다.

기존 변수에 쓰는 것이 무의미하다는 뜻은 아니다. 필수 필드나 자료형의 호환성을 확인하면서 구체적인 타입 정보를 유지하고 싶을 수 있다. 다만 “검사했다”는 말을 듣고 어느 조건을 검사했는지 생략하면 다시 같은 곳으로 돌아온다.

코드 리뷰를 한다면 `satisfies`가 존재하는지에 체크 표시만 하지 않을 것이다. 왼쪽이 리터럴인지 변수인지 본다. 객체를 만드는 위치가 어디인지 따라간다. 타입 이름이 멋있다고 일단 믿는 습관은 여기서 꽤 비싼 수업료를 청구한다.

## 11. spread: 새 객체로 위장했지만 짐은 다 가져왔습니다

기존 변수라서 통과한다면 새 객체를 만들면 되지 않을까?

JavaScript에는 참 편리한 문법이 있다. 점 세 개. 적은 글자 수로 많은 일을 할 수 있어서 좋아한다. 가끔 내가 원하지 않은 일도 같이 한다.

```ts
type Reply = { id: string };
const source = { id: "p1", debug: true };

const spreadReply = { ...source } satisfies Reply;
console.log(spreadReply.debug); // true

// @ts-expect-error: 직접 추가한 trace는 검출한다
const explicitExtra = { ...source, trace: true } satisfies Reply;

const spreadWithAnnotation: Reply = { ...source }; // 통과
console.log(JSON.stringify(spreadWithAnnotation));
// {"id":"p1","debug":true}
```

`debug`는 또 있다. 그런데 내가 직접 적은 `trace`는 걸린다.

이 예제에서 spread로 들어온 속성과 리터럴에 직접 쓴 속성은 같은 방식으로 초과 속성 검사를 받지 않는다. 바깥에 중괄호가 생겼다고 안쪽의 모든 키를 새로 쓴 것처럼 검사하는 것은 아니다.

실행 관점에서는 더 직관적이다. `{ ...source }`는 이 객체의 열거 가능한 자체 속성을 복사한다. `debug`도 복사 대상이다. **나는 “필요한 것만 골라줘”라고 쓴 적이 없다. “일단 가져와”라고 썼다.**

응답을 만들 때 `return { ...row } satisfies Reply`라고 하면 꽤 든든해 보인다. 타입도 있고 새 객체도 있다. 하지만 `row`에 있던 추가 필드가 같이 들어올 수 있다. 생성 지점에 타입 문법을 많이 써도 복사의 의미는 바뀌지 않는다.

`return { id: row.id }`는 다른 일이다. 이 코드는 무엇을 보낼지 직접 고른다. 응답 필드를 제한하는 게 목적이라면 둘의 차이가 중요하다. 이것을 짧은 코드 대 긴 코드의 취향 문제로만 보면 정작 객체가 어떻게 달라지는지 놓친다.

spread 자체가 악당인 건 아니다. 설정을 합치고 데이터를 복사할 때 잘 쓴다. 다만 집을 옮기면서 박스를 통째로 들고 왔는데 왜 필요 없는 물건까지 왔냐고 하면, 이사업체보다는 포장을 돌아봐야 한다.

## 12. 내가 직접 Exact 타입을 만들면 되잖아? — 플래그 세우지 마세요

여기서 욕심이 날 수 있다. TypeScript가 기본으로 안 해주면 내가 타입 유틸리티를 만들면 되지 않을까?

`keyof`로 키를 구하고, `Exclude`로 추가 키를 뽑고, 거기에 `never`를 붙인다. 이름도 `NoExtra`다. 이름만 보면 이번에는 정말 퇴거가 가능해 보인다.

```ts
type Reply = { id: string };

type NoExtra<Actual, Shape> = Actual &
  Record<Exclude<keyof Actual, keyof Shape>, never>;

function acceptExact<T extends Reply>(value: NoExtra<T, Reply>): T {
  return value;
}

acceptExact({ id: "p1" }); // 통과

const source = { id: "p1", debug: true };
// @ts-expect-error: 이 호출에서 debug는 never여야 하므로 거절된다
acceptExact(source);

const narrowed: Reply = source;
acceptExact(narrowed); // 통과
```

`source`를 바로 넣으면 오류가 난다. 추가 키인 `debug`의 값이 `never`여야 한다는 조건에 걸린다. 여기까지만 보면 성공이다. 나도 여기서 글을 끝냈으면 꽤 똑똑해 보였을 것이다.

그런데 `narrowed`를 넣으면 통과한다.

`narrowed`의 정적 타입은 `Reply`다. `keyof Reply`에는 `id`만 있다. 실제 객체의 `debug`를 런타임에서 찾아오는 것이 아니라, 이미 표현식에 주어진 타입 정보를 가지고 계산한다. 눈앞의 타입에 그 키가 없는데 유틸리티가 기억을 복원해 줄 수는 없다.

물론 이런 유틸리티가 쓸모없다는 뜻은 아니다. 호출 시점에 드러난 추가 키를 제한하는 API를 설계할 수 있다. 다만 위 코드는 한 단계의 키를 비교하는 실험이지, 모든 객체를 정확하게 검사하는 완성품은 아니다.

중첩 객체, 유니언, 인덱스 시그니처, 추론, 직접 지정한 타입 인자까지 고려하면 확인할 것이 더 생긴다. 컴파일 오류가 읽기 쉬운지도 봐야 한다. 추가 필드 하나 잡으려고 만들었는데 동료가 오류 메시지를 읽으려면 논문 세 편이 필요하다면 다른 비용이 생긴 것이다.

무엇보다 이것도 런타임 검증은 아니다. 외부에서 들어온 JSON이 어떤 키를 가졌는지 직접 살피지는 않는다. 타입 체조를 오래 했다고 실행 코드가 저절로 생기지는 않는다. 팔굽혀펴기로 설거지를 대체할 수 없는 것과 비슷하다. 둘 다 힘든데 결과물이 다르다.

## 13. 자동완성에서 안 보이는데 JSON에서는 정모 중

이제 내가 정말 확인했어야 할 곳으로 가보자. 편집기에서 `debug`가 보이는지가 아니라, 실제로 밖으로 나가는 데이터다.

```ts
type Reply = { id: string };

const source = { id: "p1", debug: true };
const reply: Reply = source;
const checked = source satisfies Reply;

console.log(JSON.stringify(reply));
console.log(JSON.stringify(checked));
// 둘 다 {"id":"p1","debug":true}
```

둘 다 `debug`가 있다. 여기까지 읽었으면 이제 놀랍지도 않다. 슬슬 정이 들 수도 있다. 그래도 내보내야 한다.

TypeScript의 타입 표기나 `satisfies`는 런타임 검증기로 남지 않는다. 위 코드를 실행할 때 핵심은 `const reply = source`, `const checked = source`다. 객체를 수정하는 코드가 없다. `JSON.stringify`는 편집기의 자동완성 목록을 캡처해서 보내는 함수가 아니다. 실제 객체를 직렬화한다. [타입이 제거되는 과정](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types)

이 예제에서는 속성이 단순해서 결과도 단순하다. 실제 JSON 직렬화에는 `undefined`, `toJSON`, 열거 가능 여부 같은 JavaScript 규칙도 영향을 준다. 다만 지금 확인하려는 것은 명확하다. 타입에서 키가 안 보인다는 이유만으로 직렬화에서 빠지는 것은 아니다.

그럼 실제로 필요한 필드만 골라보자.

```ts
type Reply = { id: string };

function toReply(value: Reply): Reply {
  return { id: value.id };
}

const source = { id: "p1", debug: true };
console.log(JSON.stringify(toReply(source))); // {"id":"p1"}
console.log(JSON.stringify(source)); // {"id":"p1","debug":true}
```

드디어 `debug`가 빠졌다.

꺾쇠괄호도 안 늘렸고 `never`도 안 썼다. 그냥 새 객체에 `id`만 넣었다. 너무 평범해서 오히려 허무하다. 앞에서 나는 타입 시스템의 비밀을 찾아 헤맸는데, 런타임에 속성을 안 보내려면 런타임에 속성을 안 넣으면 됐다.

다만 이것도 정확하게 봐야 한다. `toReply`가 반환하는 새 객체에서 `debug`가 빠진 것이다. 원본 `source`에는 그대로 있다. 이 함수는 원본 객체를 청소하는 함수가 아니라 응답 객체를 따로 만드는 함수다.

그리고 `id`가 실제 문자열인지 검사하는 코드도 없다. 입력이 믿을 수 있는 TypeScript 내부 값이라고 가정하고 필드를 선택한다. 외부 입력을 `as Reply`로 덮어놓고 여기에 넘기면 숫자 `id`도 그대로 복사할 수 있다.

결국 한 문제를 해결했더니 다른 질문이 남았다. **필드를 골라 보내는 것은 했는데, 그 필드의 값은 믿어도 되나?**

여기서부터는 런타임 검증의 차례다. 분량 늘리려고 새 라이브러리를 데려오는 게 아니라, 이제야 실제 값을 검사해야 하는 상황에 도착했다.

## 14. as Reply: 신분증 확인 없이 “아는 사람입니다”

외부에서 온 JSON을 받았다고 하자. 유효한 JSON이라고 해서 우리 서비스에서 유효한 데이터인 것은 아니다. 문자열 문법이 맞는지와 `id`가 문자열인지는 다른 질문이다.

```ts
type Reply = { id: string };

const raw: unknown = JSON.parse('{"id":123,"debug":true}');

// @ts-expect-error: unknown을 바로 Reply로 사용할 수 없다
const unchecked: Reply = raw;

const asserted = raw as Reply;
console.log(typeof asserted.id); // number
```

`asserted.id`는 TypeScript 관점에서 문자열이다. 실행해 보면 숫자다. `as Reply`가 숫자를 문자열로 바꾸지는 않았다. 그냥 그렇게 취급하라고 말했을 뿐이다.

여기서 `.toUpperCase()`까지 호출하면 일이 더 재밌어질 수 있지만, 독자의 런타임을 굳이 괴롭히지는 않겠다. `typeof`가 이미 할 말은 다 했다.

`unknown`을 쓰면 모르는 것을 모른다고 남겨둘 수 있다. 프로그램이 값을 받았다는 사실과, 그 값이 원하는 구조라는 사실을 분리하는 것이다. 검사 전에는 바로 `Reply`로 사용할 수 없도록 만든다.

물론 타입 가드를 직접 작성해도 된다. 객체인지, `null`은 아닌지, `id`가 있는지, 그 값이 문자열인지 확인하는 코드를 쓸 수 있다. 여기서는 추가 필드를 어떻게 처리할지 비교하기 위해 Valibot을 쓴다.

이제 우리가 원하는 것은 컴파일러에게 보여줄 타입 이름만이 아니다. 실행 중 값을 검사하고, 실패를 알려주고, 필요하다면 출력 객체를 구성하는 코드다. 이 일을 시킬 도구를 데려왔으니 주문도 정확하게 해야 한다.

“좀 엄격하게 해주세요”는 애매하다. 추가 필드를 없앨 건지, 추가 필드가 있으면 입력을 거절할 건지, 추가 필드는 남겨둘 건지가 다르다. 식당에서 “건강하게 해주세요”라고 했더니 양을 절반으로 줄여주는 것과 비슷한 커뮤니케이션 사고를 피해야 한다.

## 15. 드디어 실제로 일하는 사람을 데려왔다: Valibot

`debug`를 만났을 때 할 수 있는 일은 하나가 아니다.

| 선택 | Valibot 스키마 | `debug`의 운명 |
| --- | --- | --- |
| 필요한 필드만 출력에 넣는다 | `object` | 출력에서 빠짐 |
| 모르는 필드가 오면 오류로 처리한다 | `strictObject` | 입력이 검증 실패 |
| 추가 필드를 남겨둔다 | `looseObject` | 출력에도 남음 |
| 추가 필드도 정해진 조건으로 검사한다 | `objectWithRest` | 조건을 만족하면 남음 |

이 표는 일반적인 JSON 형태의 객체를 기준으로 읽으면 된다. `looseObject`와 `objectWithRest`는 일부 키를 보안상 필터링하므로, 모든 JavaScript 객체의 모든 속성을 무조건 복제한다고 일반화하지는 않는다. 세부 정책은 [객체 가이드](https://valibot.dev/guides/objects/)에서 확인할 수 있다.

TypeScript의 리터럴 검사와 중요한 차이도 있다. 여기서는 스키마가 실제로 실행된다. 변수를 한 번 거쳤다고 파싱 정책이 없어지지 않는다. `source`라는 이름의 추천서를 받아와도 파서는 입력을 본다.

### object: 손님은 받는데 짐은 여기 두고 가세요

```ts
import * as v from "valibot";

const ReplySchema = v.object({
  id: v.string(),
});

const input = { id: "p1", debug: true };
const output = v.parse(ReplySchema, input);

console.log(JSON.stringify(output)); // {"id":"p1"}
console.log(JSON.stringify(input)); // {"id":"p1","debug":true}
console.log(output === input); // false
```

이번에는 진짜로 출력에서 `debug`가 빠졌다. `v.parse`가 `object` 스키마를 실행했고, 선언한 속성에 맞춰 출력을 만들었기 때문이다. [object API](https://valibot.dev/api/object/)

중요한 것은 마지막 두 줄이다. 원본 `input`에는 여전히 `debug`가 있다. 출력과 원본도 같은 객체가 아니다. 그래서 코드에서 **파싱 결과를 써야 한다.**

이 문장은 너무 당연해 보여서 오히려 지나치기 쉽다. 다음 두 함수를 비교하면 왜 굳이 말하는지 보인다.

```ts
import * as v from "valibot";

const ReplySchema = v.object({ id: v.string() });

function parseButReturnOriginal(input: unknown): unknown {
  v.parse(ReplySchema, input);
  return input;
}

function returnParsed(input: unknown) {
  return v.parse(ReplySchema, input);
}

const input = { id: "p1", debug: true };
console.log(JSON.stringify(parseButReturnOriginal(input)));
// {"id":"p1","debug":true}
console.log(JSON.stringify(returnParsed(input)));
// {"id":"p1"}
```

`parseButReturnOriginal`도 파싱을 한다. 그래서 코드 검색으로 `parse`가 호출되는지만 보면 검증하는 함수가 맞다. 그런데 반환하는 것은 원본이다. 힘들게 정리해 놓은 출력은 버리고, 처음 받은 객체를 다시 내보낸다.

검증 통과 도장을 찍은 뒤 옆에 준비된 결과물은 두고 원본을 들고 가는 셈이다. 나는 필요한 필드만 보내고 싶었는데, 실제로 반환한 객체에는 여전히 `debug`가 있다.

두 번째 함수는 파싱 출력을 반환한다. 여기서는 추가 필드가 빠진 객체가 나간다. 기본값이나 변환이 있는 스키마라면 이런 차이는 더 중요해진다. 파싱했다는 사실과 파싱한 결과를 사용한다는 사실은 반드시 구분해야 한다.

`object`가 추가 필드를 거절한 것도 아니다. 입력에 `debug`가 있어도 성공했다. 출력에서 제외했을 뿐이다. 요청에 알 수 없는 키가 들어온 것 자체를 오류로 알려야 한다면, 아직 원하는 정책이 아니다.

### strictObject: 명단에 없는 분이 계시면 오늘 모임 취소입니다

```ts
import * as v from "valibot";

const ReplySchema = v.strictObject({
  id: v.string(),
});

const result = v.safeParse(ReplySchema, {
  id: "p1",
  debug: true,
});

console.log(result.success); // false
if (!result.success) {
  console.log(result.issues.length); // 이 입력에서는 1
}
```

이번에는 입력이 검증에 실패한다. `debug`를 조용히 버리고 진행하는 대신, 알 수 없는 속성이 들어왔다는 사실을 오류로 만든다. [strictObject API](https://valibot.dev/api/strictObject/)

이 차이는 수정 API에서 생각해 보면 체감하기 쉽다. 호출자가 `displayName`을 바꾸려다가 `displayNmae`라고 보냈다. 서버는 그 필드를 조용히 제외했다. 요청은 성공했는데 이름이 안 바뀌었다.

> 클라이언트: 성공했다면서요.
> 서버: 저는 할 일을 안 했고, 할 일이 없었으니 성공했습니다.

둘 다 당당해서 더 답답한 상황이다. 이런 입력에서 추가 키를 오류로 알려주면 “요청 형식을 잘못 보냈다”는 사실을 드러낼 수 있다. 조용히 버리는 정책과 거절하는 정책 중 무엇이 맞는지는 API의 의도에 달려 있다.

반대로 서로 다른 버전의 클라이언트와 서버가 함께 동작해야 하는 경우를 생각해 보자. 새 클라이언트가 추가한 필드를 이전 서버가 모를 수 있다. 알 수 없는 필드를 항상 거부하면 호환성에 영향을 준다. `strict`라는 이름이 붙었다고 모든 상황에서 더 좋은 답인 것은 아니다. 엄격한 정책도 요구사항이 있어야 한다.

위 코드는 `safeParse`를 써서 `success`로 결과를 확인했다. `parse`는 검증 실패를 예외로 전달한다. 실패를 처리하는 방식의 차이이지, `safeParse`니까 잘못된 입력도 대충 허용한다는 뜻은 아니다.

또 `issues.length`가 1이라고 추가 키가 하나였다는 뜻으로 읽지 않는다. `strictObject`는 알 수 없는 속성에 대해 하나의 이슈를 반환하도록 설계되어 있다. 오류 목록의 길이를 세어 입력의 모든 사정을 역추적하려고 하면 또 약관을 놓치게 된다.

### looseObject: 일단 같이 들어오세요. 대신 보증은 안 합니다

```ts
import * as v from "valibot";

const ReplySchema = v.looseObject({
  id: v.string(),
});

const output = v.parse(ReplySchema, {
  id: "p1",
  debug: true,
});

console.log(JSON.stringify(output)); // {"id":"p1","debug":true}
```

`debug`가 다시 살아남았다. 이번에는 의도한 생존이다. 선언한 `id`는 검사하고, 예제의 추가 속성은 출력에 남긴다. [looseObject API](https://valibot.dev/api/looseObject/)

일부 필드만 알고 있고 나머지 확장 정보를 유지해야 하는 데이터라면 이런 정책이 필요할 수 있다. 문제는 이것을 “입력 전체를 다 검증했다”로 읽을 때다. `id`에 `v.string()`을 적었지만 `debug`에 `v.boolean()`을 적은 것은 아니다. 보존과 검증은 다른 일이다.

추가 속성을 다음 코드에서 사용하려면 그 값에 대해 무엇을 알고 있는지 확인해야 한다. 출력에 들어 있다고 해서 업무적으로 믿을 수 있는 값이라는 도장이 찍힌 것은 아니다.

“원본 정보를 최대한 잃지 않고 저장한다”와 “외부로 공개할 필드만 반환한다”는 요구는 다를 수 있다. 같은 스키마를 재사용하면 코드가 줄어서 기분은 좋다. 하지만 서로 반대 방향의 정책까지 하나로 합쳤다면, 줄어든 코드만큼 고민도 삭제한 셈이다.

### objectWithRest: 동반 입장 가능. 그런데 전원 불리언이셔야 합니다

```ts
import * as v from "valibot";

const ReplySchema = v.objectWithRest(
  { id: v.string() },
  v.boolean(),
);

const accepted = v.safeParse(ReplySchema, {
  id: "p1",
  debug: true,
  preview: false,
});

const rejected = v.safeParse(ReplySchema, {
  id: "p1",
  debug: "yes",
});

console.log(accepted.success); // true
if (accepted.success) {
  console.log(JSON.stringify(accepted.output));
  // {"id":"p1","debug":true,"preview":false}
}
console.log(rejected.success); // false
```

여기서는 이름이 정해진 `id`는 문자열이고, 나머지 속성은 불리언이어야 한다. 그래서 `debug: true`와 `preview: false`는 통과하지만 `debug: "yes"`는 실패한다. 문자열로 힘차게 긍정해도 불리언은 아니다. [objectWithRest API](https://valibot.dev/api/objectWithRest/)

첫 번째 인자는 정해진 속성의 스키마이고, 두 번째 인자는 나머지 속성에 적용할 스키마다. `id`까지 불리언이어야 하는 것은 아니다. 둘의 담당 구역이 다르다.

추가 키가 여러 개이고 그 값에 공통 규칙이 있다면 생각해 볼 만하다. 다만 “나머지 값은 불리언”과 “허용한 기능 이름만 키로 쓸 수 있다”는 다른 계약이다. 위 스키마는 `debug`, `preview`라는 두 이름만 허용한다고 선언한 것이 아니다. 키 이름 자체의 제한이 필요하면 그 조건도 별도로 설계해야 한다.

이제 `debug` 하나를 처리하는 방법이 네 개가 됐다. 삭제, 거절, 보존, 조건부 허용. 처음에는 타입 검사를 강하게 할지 약하게 할지 정도로 생각했는데, 실제로는 서로 다른 데이터 처리 정책이었다.

TypeScript한테 “알아서 엄격하게”라고 주문했던 내가 문제를 얼마나 뭉뚱그려 생각했는지 보인다. 알아서 해주길 바랐지만 무엇을 할지부터 내가 몰랐다. 컴파일러도 난감했을 것이다.

## 16. 바깥에 strict 붙였으니 안쪽도 strict겠지? — 자동 확장 서비스는 없습니다

이번에는 객체 안에 객체가 있다. `strictObject`를 바깥에 크게 붙였으니 안쪽도 다 엄격하게 검사할 것 같다. 이름이 주는 안정감이란 대단하다.

```ts
import * as v from "valibot";

const EnvelopeSchema = v.strictObject({
  payload: v.object({ id: v.string() }),
});

const nestedExtra = v.safeParse(EnvelopeSchema, {
  payload: { id: "p1", debug: true },
});

const outerExtra = v.safeParse(EnvelopeSchema, {
  payload: { id: "p1" },
  debug: true,
});

console.log(nestedExtra.success); // true
if (nestedExtra.success) {
  console.log(JSON.stringify(nestedExtra.output));
  // {"payload":{"id":"p1"}}
}
console.log(outerExtra.success); // false
```

바깥 `debug`는 실패한다. 안쪽 `debug`는 실패시키지 않고 출력에서 빠진다.

바깥 스키마는 `strictObject`이고, `payload` 스키마는 `object`다. 각각 자기 구역의 정책을 실행한다. 바깥에 strict를 붙였다고 안쪽 스키마의 종류까지 바뀌지는 않는다.

이것도 코드에 적힌 것을 보면 당연하다. 그런데 “엄격한 스키마를 썼다”라고 문장 하나로 기억하면 안쪽의 `object`는 잊어버리기 쉽다. 도구의 이름만 기억하고 실제 배치를 놓치는 패턴이 또 나온다.

오히려 이런 혼합이 필요한 경우도 있다. 요청의 바깥 형식은 고정하고, 내부 메타데이터에는 확장을 허용할 수 있다. 모든 단계를 같은 정책으로 도배하는 것보다 각각의 목적에 맞게 선택하는 편이 낫다.

버그를 찾을 때는 추가 키가 어느 객체 안에 있는지부터 따라가면 된다. 루트 스키마 이름을 보고 “우리 strict 쓰는데?”라고 끝내면, 안쪽의 `debug`는 계속 편하게 살 수 있다. 전입신고는 다른 동네에 되어 있었다.

## 17. InferOutput을 썼는데요. 파싱한 거랑 같은 거 아닌가요?

스키마를 만들었으니 타입도 거기서 뽑으면 된다. 필드를 두 번 적지 않아서 좋다. 그런데 여기서도 마지막으로 한 번 더 헷갈릴 수 있다.

```ts
import * as v from "valibot";

const ReplySchema = v.object({ id: v.string() });
type Reply = v.InferOutput<typeof ReplySchema>;

const source = { id: "p1", debug: true };
const assigned: Reply = source; // 구조적 호환성으로 통과
const parsed = v.parse(ReplySchema, source);

console.log(JSON.stringify(assigned)); // {"id":"p1","debug":true}
console.log(JSON.stringify(parsed)); // {"id":"p1"}
```

`assigned`에는 `debug`가 남고 `parsed`에서는 빠진다.

`Reply`가 Valibot 스키마에서 나왔다는 사실은 맞다. 하지만 그 타입을 변수에 붙이는 순간 TypeScript의 정적 호환성 규칙을 따른다. 스키마를 실행한 것이 아니다. 출신 학교가 Valibot이라고 타입이 런타임 검증 업무까지 수행하지는 않는다.

`InferOutput`은 스키마의 출력 타입을 얻는다. `InferInput`은 스키마가 기대하는 입력 타입을 얻는다. 변환이나 기본값이 있는 경우에는 둘이 달라질 수 있다. 그렇다고 이 타입을 선언하는 것이 데이터를 파싱한 증거가 되지는 않는다. [Valibot 타입 추론](https://valibot.dev/guides/infer-types/)

코드에서 실제로 통과한 출력을 사용하고 싶다면 그 흐름을 남기는 것이 분명하다.

```ts
import * as v from "valibot";

const ReplySchema = v.object({ id: v.string() });

function readReply(input: unknown) {
  const result = v.safeParse(ReplySchema, input);
  if (!result.success) {
    return { kind: "invalid" as const, issues: result.issues };
  }
  return { kind: "valid" as const, value: result.output };
}

const result = readReply({ id: "p1", debug: true });
if (result.kind === "valid") {
  console.log(JSON.stringify(result.value)); // {"id":"p1"}
}
```

여기서는 `unknown`을 받아 파싱하고, 성공한 경우에 `result.output`을 전달한다. 호출자는 `kind`로 분기한 다음 그 출력을 쓴다. 파싱 결과를 버리고 원본을 돌려주지도 않고, `as Reply`로 잠깐 눈을 감지도 않는다. [safeParse 결과 사용](https://valibot.dev/api/safeParse/)

실패를 예외로 던질지, 결과 값으로 반환할지는 서비스의 에러 처리 방식에 따라 달라질 수 있다. 이 글에서는 추가 필드가 어떻게 처리되는지 보려고 작은 결과 타입으로 나눴다. 중요한 것은 성공 경로에서 어떤 객체가 다음 코드로 가는지다.

여기까지 와서야 `debug`를 다루는 일이 정리된다. 타입으로 안 보이게 하는 것, 타입 검사에서 잡는 것, 파싱 출력에서 제거하는 것, 입력 자체를 거절하는 것은 서로 다른 일이다. 이름에 `Reply`가 공통으로 들어 있다고 같은 기능이 되지는 않는다.

## 18. TypeScript는 잘못이 없고, 나는 요구사항을 구두로 전달했다

처음에는 타입스크립트가 추가 필드를 놓친다고 생각했다. 이제 보니 내가 적어놓은 계약과 기대한 결과가 달랐다.

나는 “문자열 `id`가 있으면 된다”에 가까운 타입을 적어놓고, 마음속으로는 “`id` 빼고 다 나가”를 외치고 있었다. 컴파일러는 내 마음을 타입 추론하지 않는다. ~~해주면 좋겠는데, 해주면 더 무서울 것 같기도 하다.~~

다음에 비슷한 코드를 보면 우선 원하는 결과부터 분리할 생각이다.

- **객체를 쓰는 순간 오타를 잡고 싶다.** 생성 지점의 타입 표기나 `satisfies`를 본다. 필드를 직접 쓰는 자리인지, 변수나 spread를 거친 자리인지도 확인한다.
- **이 값을 받는 함수가 `id`를 쓸 수 있으면 된다.** 구조적 호환성이 원래 하던 일을 하게 둔다. 추가 정보를 보존할 필요가 있는지도 판단한다.
- **응답에서 특정 필드만 보내고 싶다.** 실제 객체를 구성한다. 명시적으로 필드를 고르거나, 목적에 맞는 파싱 출력을 반환한다.
- **요청에 모르는 키가 오면 실패시켜야 한다.** 입력 경계에서 그 정책을 실행한다. 조용히 버리는 것과 오류로 거부하는 것을 구별한다.

전부 “추가 필드를 막는다”로 줄여 말할 수는 있다. 하지만 그렇게 줄인 순간 내가 무슨 일을 시키는지 다시 애매해진다. 글이 이렇게 길어진 이유도 아마 내가 질문을 너무 짧게 했기 때문일 것이다. 독자는 무슨 죄인가 싶지만 여기까지 왔으니 같이 책임져주셨으면 한다.

실제 코드를 읽을 때도 순서가 생겼다. 먼저 표현식에 어떤 타입이 잡혔는지 보고, 받는 쪽의 타입이나 함수 시그니처를 확인한다. 리터럴인지 변수인지, 직접 적은 속성인지 펼쳐 온 속성인지 본다. 그다음 런타임에 어떤 객체가 만들어지고 반환되는지 따라간다.

이 순서대로 보면 `as`를 붙여 빨간 줄을 없앤 것과 잘못된 계약을 고친 것을 구분하기 쉽다. “빌드가 됩니다”는 반가운 소식이지만 “원하는 데이터만 나갑니다”의 동의어는 아니다.

처음 출발점은 `db.transaction<…>` 호출 하나였다. 결과에 쓸 타입을 적었는데 왜 필드가 더 들어가냐는 작은 의문이었다. DB를 의심하고, 제네릭을 의심하고, 콜론 위치를 보고, spread를 지나서, 결국 실행 중인 객체를 보게 됐다.

생각보다 멀리 왔다. `debug` 하나 내보내려고 출발했는데 내가 먼저 타입 공부를 하고 있었다.

그래도 이제 원하는 말은 할 수 있다.

> “id가 있는지만 봐주세요”와 “id만 남겨주세요”는 다른 주문입니다.

타입스크립트야. 앞에서는 누구 편이냐고 해서 미안하다.

근데 변수 한 번 거쳤더니 통과하는 건 처음 보면 진짜 좀 억울하긴 해.
