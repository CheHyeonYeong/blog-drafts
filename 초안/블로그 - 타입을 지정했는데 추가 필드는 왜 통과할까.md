# 타입을 지정했는데 추가 필드는 왜 통과할까?

> 작성 근거: [[2026-10-20]]의 `db.transaction<…>` 메모, [[2026-10-26]]의 “타입 오류가 적재적소에 뜨도록 하자”.
> 업무 중 생긴 의문에서 출발했지만, 아래 코드는 설명을 위해 새로 만든 독립 예제다. 특정 DB 라이브러리의 내부 구현이나 실제 서비스의 장애를 재현한 글은 아니다.
> 검증 기준: TypeScript 5.9.3 / 6.0.3, `strict`, `target: ES2022`, Valibot 1.1.0. 최신 버전 소개가 아니라 명시한 버전으로 결과를 고정한 실험이다.

TypeScript로 코드를 작성하다가 이상한 상황을 만났다. `db.transaction<…>` 호출에 결과로 사용할 타입을 적었는데, 콜백이 반환한 객체에 추가 필드가 있어도 오류가 나지 않았다. 필요한 필드의 타입을 틀리게 쓰면 오류가 났지만, 필요 없는 필드를 하나 더 넣는 것은 통과했다.

그때는 이렇게 메모했다.

“TypeScript는 필요한 필드가 있으면 추가 필드가 있어도 호환되는구나.”

그런데 이 설명만으로는 충분하지 않았다. 다른 곳에서 객체를 만들 때는 타입에 없는 필드에 분명히 빨간 줄이 나타났다. 추가 필드가 허용된다면 그 오류는 왜 생길까? 허용되지 않는다면 변수를 한 번 거쳤을 때는 왜 통과할까?

처음에는 타입을 좀 더 엄격하게 적으면 해결할 수 있는 문제라고 생각했다. 반환 타입을 명시하고, `satisfies`를 붙이고, 제네릭 제약을 추가하면 언젠가는 객체의 모양이 정확히 고정될 것 같았다. 하지만 코드를 나눠 보니 이 기능들은 서로 다른 질문에 답하고 있었다.

이 글에서는 객체 하나를 계속 바꿔 보면서 다음 질문을 따라간다.

1. TypeScript가 두 객체 타입을 호환된다고 판단하는 기준은 무엇인가?
2. 같은 속성을 가진 객체도 작성 위치에 따라 검사 결과가 달라지는 이유는 무엇인가?
3. 함수의 반환 타입, 함수 전체의 타입, 제네릭의 타입 인자는 어떻게 다른가?
4. `satisfies`와 spread는 어디까지 검사하며, 무엇을 바꾸지 않는가?
5. 런타임에 추가 필드를 제거하거나 거부하려면 어떤 코드가 필요한가?

뒤에서는 Valibot의 `object`, `strictObject`, `looseObject`, `objectWithRest`를 같은 입력으로 실행해 본다. TypeScript에서 시작한 의문이 런타임 스키마까지 이어지는 이유는 단순하다. 내가 기대했던 “정확한 객체”라는 말 안에 타입 검사와 실제 데이터 처리가 섞여 있었기 때문이다.

각 TypeScript 코드 블록은 별도 파일로 실행할 수 있도록 작성했다. 오류를 의도한 줄에는 `@ts-expect-error`를 붙였다. 이 주석은 오류를 없애는 해결책이 아니라, 바로 다음 줄에서 오류가 발생해야 한다는 검증 표시다. 실제 진단을 보고 싶다면 주석을 지우면 된다.

## 1. 객체에 있는 속성과 타입으로 보이는 속성

설명을 위해 응답 타입을 아주 작게 시작하자.

```ts
type Reply = {
  id: string;
};

const source = {
  id: "p1",
  debug: true,
};

const reply: Reply = source;

console.log(reply.id); // p1
// @ts-expect-error: Reply에는 debug가 선언되어 있지 않다
console.log(reply.debug); // 실행하면 true
console.log(reply === source); // true
```

`source`의 추론 타입에는 `id`와 `debug`가 모두 있다. 반면 `reply`는 `Reply`로 선언했으므로, 그 변수를 통해 사용할 수 있다고 알려진 속성은 `id`다. 그래서 `reply.debug`를 작성하면 타입 오류가 난다.

여기서 바로 질문 하나를 분리해야 한다. `reply.debug`가 타입 오류라는 사실은 실제 객체에 `debug`가 없다는 뜻일까?

그렇지 않다. 대입문에는 객체를 복사하거나 속성을 삭제하는 코드가 없다. `reply`와 `source`는 같은 객체를 참조한다. 타입 오류가 있어도 코드를 출력하도록 컴파일해 실행하면 `reply.debug`의 값은 `true`다. 물론 실제 프로젝트에서는 오류가 있는 코드를 그대로 배포하자는 뜻이 아니다. 정적 검사 결과와 실행 결과가 서로 다른 층위에 있다는 것을 관찰하는 실험이다.

이 예제에는 세 가지가 있다. 실제 객체는 `{ id: "p1", debug: true }`이고, `source`의 정적 타입은 두 속성을 알고 있으며, `reply`의 정적 타입은 `id`만 노출한다. 객체가 바뀐 것이 아니라 그 객체를 다루는 표현식에 주어진 타입 정보가 달라졌다.

타입을 더 작게 적는 일과 데이터를 더 작게 만드는 일을 혼동하면 이후의 설명이 계속 헷갈린다. 이 차이를 먼저 잡아두면 반환 타입과 JSON 직렬화도 같은 원리로 읽을 수 있다.

## 2. 구조적 타이핑은 어떤 질문에 답할까?

TypeScript의 객체 타입 호환성은 대체로 구조를 기준으로 판단한다. 타입 이름이 같은지보다, 대상 타입이 요구하는 멤버를 값이 제공하는지가 중요하다. 다음 함수는 `id`만 사용한다.

```ts
type Reply = { id: string };

function printId(value: Reply): void {
  console.log(value.id);
}

const fromDatabase = {
  id: "p1",
  createdAt: "2026-10-29",
  internalNote: "example",
};

printId(fromDatabase); // 통과
```

`printId`를 실행하는 데 필요한 것은 문자열 `id`다. `fromDatabase`에는 그 조건이 충족되어 있다. 다른 속성을 더 가지고 있어도 `value.id`를 읽는 계약은 깨지지 않는다. TypeScript는 이런 객체를 `Reply`를 요구하는 자리에 전달할 수 있게 한다. [타입 호환성의 기본 규칙](https://www.typescriptlang.org/docs/handbook/type-compatibility.html)

이 규칙은 객체를 여러 함수에서 재사용할 때 유용하다. 조회한 객체에 속성이 열 개 있다고 해서, 그중 한 속성만 읽는 함수마다 별도 객체를 반드시 만들어야 한다면 불편할 것이다. 함수가 필요한 부분을 타입으로 선언하고 더 많은 정보를 가진 값을 받아들이는 방식에는 분명한 용도가 있다.

다만 “필요한 속성이 있으면 된다”를 모든 TypeScript 타입에 적용하는 만능 규칙으로 외우면 안 된다. 함수 매개변수의 호환성, 클래스의 private/protected 멤버, 유니언, 인덱스 시그니처 등에는 추가로 고려할 조건이 있다. 이 글은 우선 필수 속성 `id: string`을 가진 평범한 객체에 범위를 좁힌다.

또한 구조적으로 호환된다는 말은 속성의 자료형을 무시한다는 뜻이 아니다. `id: number`를 전달하거나 `id`를 빠뜨리는 것은 다른 문제다.

```ts
type Reply = { id: string };

const wrongType = { id: 123, debug: true };
const missingId = { debug: true };

// @ts-expect-error: id는 string이어야 한다
const a: Reply = wrongType;

// @ts-expect-error: 필수 속성 id가 없다
const b: Reply = missingId;
```

변수에 넣으면 모든 오류를 피할 수 있는 것이 아니다. 추가 속성의 유무와 필수 속성의 호환성은 구분해서 봐야 한다. 변수를 거친 객체라도 대상 타입을 만족하지 않으면 여전히 오류가 발생한다.

## 3. 그렇다면 객체 리터럴에는 왜 빨간 줄이 생길까?

앞의 설명만 들으면 다음 코드도 통과할 것 같다.

```ts
type Reply = { id: string };

// @ts-expect-error: 객체 리터럴에 직접 작성한 추가 속성
const direct: Reply = { id: "p1", debug: true };

const source = { id: "p1", debug: true };
const indirect: Reply = source; // 통과
```

두 경우의 실제 값에는 같은 필드가 있다. 차이는 그 값을 타입에 맞춰 검사하는 자리다. 첫 번째는 새 객체 리터럴을 `Reply`에 직접 대입한다. 두 번째는 이미 타입이 추론된 변수의 값을 대입한다.

첫 번째 자리에는 **초과 속성 검사(excess property checking)**가 적용된다. 객체를 특정 타입에 맞춰 직접 작성할 때 알 수 없는 속성이 들어오면, 작성자가 오타를 냈거나 타입을 잘못 이해했을 가능성을 알려준다. [공식 객체 타입 문서](https://www.typescriptlang.org/docs/handbook/2/objects.html#excess-property-checks)

예를 들어 설정에 `timeout`을 넣으려다 `timeuot`이라고 적었다고 하자. 추가 속성을 언제나 허용하면 이런 실수를 놓치기 쉽다. 반면 이미 다른 용도로 만든 객체를 전달할 때마다 모든 추가 속성을 금지하면 구조적 타이핑의 유용함이 줄어든다. TypeScript는 객체 리터럴의 일부 사용 지점에서 추가 검사를 수행한다.

그래서 이 현상을 “변수에 넣어서 타입 검사를 우회했다”라고만 설명하면 중요한 부분을 놓친다. 일반적인 호환성 검사 자체가 사라진 것은 아니다. 새 객체 리터럴에 적용되던 초과 속성 검사가 같은 방식으로 적용되지 않는 것이다.

이 설명에서 종종 *fresh object literal*이라는 표현을 만나게 된다. 여기서 fresh는 객체를 만든 지 몇 초가 지났다는 뜻이 아니다. 컴파일러가 표현식을 다루는 방식과 관련된 말이다. 시간이나 실행 순서에 따른 규칙으로 이해하면 안 된다.

실무에서는 “이 객체는 fresh인가?”라는 용어 암기보다 “지금 새 리터럴을 목표 타입에 직접 맞추고 있는가, 이미 있는 값의 호환성을 확인하는가?”를 먼저 물어보는 편이 예제를 읽기 쉽다. 단, spread처럼 리터럴 내부의 일부 속성이 다른 경로로 들어오는 경우는 뒤에서 다시 구분한다.

## 4. 옵션 객체와 필수 필드에서 생기는 오해

초과 속성 검사는 특히 옵션 객체에서 의미가 잘 드러난다.

```ts
type Options = {
  timeout?: number;
  retries?: number;
};

function configure(options: Options): void {
  console.log(options);
}

// @ts-expect-error: timeout을 잘못 적었다
configure({ timeuot: 1000 });

const typoOnly = { timeuot: 1000 };
// @ts-expect-error: Options와 공통 속성도 없는 객체다
configure(typoOnly);

const mixed = { timeout: 1000, timeuot: 2000 };
configure(mixed); // 통과
```

이 예제는 “변수로 빼면 추가 속성 검사는 무조건 안 한다”라는 기억을 경계하게 만든다. 모든 속성이 optional인 타입에는, 전달한 객체와 공통 속성이 전혀 없을 때 오류가 발생하는 경우가 있다. 여기서는 `typoOnly`가 그런 경우다. `mixed`는 실제 `timeout`도 가지고 있어서 결과가 달라진다.

따라서 에러 메시지에 나타난 이유를 읽는 습관이 중요하다. `id`가 빠졌다는 오류, 속성 값의 타입이 다르다는 오류, 알 수 없는 속성이라는 오류, 공통 속성이 없다는 오류는 모두 같은 뜻이 아니다. 빨간 줄이 사라지는 방법만 찾으면 어떤 검사가 작동했는지 알기 어렵다.

그렇다면 옵션 타입에 `[key: string]: unknown`을 넣으면 어떨까? 문자열 이름의 속성을 열어두면 추가 키를 허용할 수 있다. 하지만 그것은 오류를 지우는 장식이 아니라 타입의 계약을 바꾸는 일이다. 임의의 키가 실제로 허용되는 설정이라면 적절하지만, 정해진 옵션만 받아야 한다면 오타를 놓치게 만드는 선택이 될 수 있다.

타입을 고칠 때는 “컴파일러를 만족시키는가”와 “의도한 입력 범위를 표현하는가”를 함께 확인해야 한다. 지금은 `debug`가 편리한 예제지만, 실제로는 `timeuot`처럼 아무 효과도 없는 속성이 조용히 지나갈 수 있기 때문이다.

## 5. 함수에 반환 타입을 적으면 정확한 객체가 될까?

제네릭 없이 일반 함수부터 보자. 반환 타입을 명시하고 객체 리터럴을 직접 반환하는 경우다.

```ts
type Reply = { id: string };

function makeDirect(): Reply {
  // @ts-expect-error: 반환 타입에 없는 속성을 직접 작성했다
  return { id: "p1", debug: true };
}

function makeThroughVariable(): Reply {
  const source = { id: "p1", debug: true };
  return source; // 통과
}
```

두 함수에는 모두 `: Reply`가 있다. 하지만 첫 번째의 `return`에는 리터럴이 있고, 두 번째의 `return`에는 변수가 있다. 앞에서 본 대입 예제와 같은 차이를 함수 안에서도 관찰할 수 있다.

반환 타입을 명시하면 함수가 돌려주는 값이 `Reply`와 호환되는지 검사할 수 있다. 새 리터럴을 직접 반환하는 지점에서는 초과 속성도 잡는다. 그렇다고 함수가 반환할 수 있는 모든 객체의 실제 키를 `id` 하나로 제한한 것은 아니다.

이 구분은 함수의 공개 API를 설계할 때 중요하다. 호출자는 `makeThroughVariable()`의 결과를 `Reply`로 다룬다. 내부에서 `debug`를 추가했다고 호출자에게 그 속성의 타입 정보까지 자동으로 노출되지는 않는다. 그러나 런타임 객체에는 여전히 `debug`가 있다. 반환 타입은 호출자가 의존할 수 있는 정적 계약을 설명하고, 함수 본문은 실제로 어떤 값을 만드는지 결정한다.

그래서 반환 타입을 적는 것 자체는 여전히 가치가 있다. 구현을 바꾸다가 필수 필드를 누락하거나, 다른 자료형을 반환하는 실수를 함수 경계에서 발견할 수 있다. 다만 그 가치에 “불필요한 속성을 런타임에서 제거한다”는 기능까지 더해서 기대하면 안 된다.

여기서는 예제를 단순하게 만들기 위해 동기 함수를 쓴다. `Promise<Reply>`를 반환하는 비동기 함수에서도 정적 계약과 실제 객체를 구분해야 한다는 점은 같다. 비동기라는 이유로 객체를 정제하는 코드가 자동으로 추가되지는 않는다.

## 6. 함수 전체에 타입을 붙이는 것과 반환 위치에 붙이는 것

다음 두 줄은 비슷하게 보이지만 같은 위치에 타입을 적은 것이 아니다.

```ts
type Reply = { id: string };

const inferredFunction: () => Reply = () => ({
  id: "p1",
  debug: true,
}); // 통과

const explicitReturn = (): Reply => ({
  id: "p1",
  // @ts-expect-error: 반환 타입을 명시한 리터럴의 추가 속성
  debug: true,
});
```

첫 번째의 `: () => Reply`는 `inferredFunction`이라는 변수에 할당할 함수 타입이다. 오른쪽 화살표 함수가 그 함수 타입에 호환되는지를 확인한다. 이 예제에서 더 많은 속성을 반환하는 함수는 `Reply`를 반환하는 함수로 사용할 수 있다.

두 번째의 `(): Reply =>`는 화살표 함수 자체의 반환 타입 표기다. 이 반환 위치에서 직접 만든 리터럴이 `Reply`에 맞춰 검사된다. 이 차이를 보지 않고 “둘 다 반환 타입을 적었는데 왜 다르지?”라고 생각하면 제네릭이 끼어들었을 때 훨씬 복잡해진다. [함수 타입 표현식과 반환 타입 표기](https://www.typescriptlang.org/docs/handbook/2/functions.html)

여기서 함수의 반환값이 더 많은 정보를 가질 수 있다는 점은 사용 방향으로 생각하면 이해하기 쉽다. `id`를 가진 값을 돌려줄 함수가 필요한 곳에, `id`와 `debug`를 가진 값을 돌려줄 함수를 제공해도 호출자는 `id`를 읽을 수 있다. 추가 정보를 읽겠다고 약속하지 않았을 뿐이다.

물론 이것은 함수 타입 호환성의 모든 규칙을 설명한 것은 아니다. 매개변수 방향의 검사에는 다른 고려가 들어가므로, 반환값에서 성립한 설명을 매개변수에 그대로 뒤집어 적용하지 않는다. 이 글의 관심사는 반환 객체에 있는 추가 속성이다.

내가 처음 겪은 상황을 조사한다면, 이제 단순히 `Reply`라는 글자가 있는지만 찾지 않을 것이다. 함수 자체의 반환 타입인지, 변수에 붙인 함수 타입인지, 콜백을 받는 함수의 인자 타입인지부터 구분해야 한다.

## 7. 제네릭은 반환 타입을 뜻하는 문법이 아니다

처음 초안을 쓸 때는 “제네릭에 반환 타입을 지정했다”라고 줄여 말했다. 하지만 `<T>` 자체가 반환 타입을 뜻하지는 않는다. 타입 매개변수는 함수 시그니처의 여러 위치에 사용될 수 있고, 어느 위치에 등장하느냐에 따라 연결하는 관계가 달라진다.

아래의 함수에서는 그 관계가 코드에 직접 보인다.

```ts
type Reply = { id: string };

function run<T>(work: () => T): T {
  return work();
}

const result = run<Reply>(() => ({ id: "p1", debug: true }));

// @ts-expect-error: id의 자료형은 여전히 검사한다
run<Reply>(() => ({ id: 123 }));

// @ts-expect-error: id가 없는 반환값도 허용되지 않는다
run<Reply>(() => ({ debug: true }));
```

여기서 `T`는 두 곳에 등장한다. `work`라는 콜백의 반환 타입, 그리고 `run` 자체의 반환 타입이다. `run<Reply>`라고 호출하면 이 두 위치에 `Reply`를 사용하겠다는 뜻이다. `T`라는 글자나 꺾쇠괄호가 특별히 반환 타입을 의미해서가 아니라, 이 함수의 선언이 그렇게 연결되어 있다. [제네릭의 타입 매개변수](https://www.typescriptlang.org/docs/handbook/2/generics.html)

첫 번째 호출이 통과하는 동작을 보기 위해 제네릭은 꼭 필요하지도 않다. 시그니처를 고정해도 같은 관찰을 할 수 있다.

```ts
type Reply = { id: string };

function runReply(work: () => Reply): Reply {
  return work();
}

const result = runReply(() => ({ id: "p1", debug: true }));
console.log(JSON.stringify(result)); // {"id":"p1","debug":true}
```

이 예제는 문제의 핵심이 “제네릭의 허점”에 있지 않다는 것을 보여준다. `() => Reply`에 호환되는 콜백인지 확인하는 과정과, 함수 반환 위치에 명시한 타입으로 리터럴을 검사하는 과정의 차이를 봐야 한다.

실제 `db.transaction`에서는 라이브러리 버전에 따라 오버로드, 비동기 반환, 트랜잭션 객체의 타입 등이 추가된다. 그래서 이 작은 예제가 특정 라이브러리의 모든 동작을 증명하지는 않는다. 실제 코드를 설명하려면 선언으로 이동해서 타입 인자가 어디에 쓰이는지 확인해야 한다.

나는 이런 경우 라이브러리 이름을 지우고도 같은 현상이 나오는지 먼저 확인하려고 한다. `runReply`만으로 재현된다면 DB 실행이나 트랜잭션의 문제가 아니라 함수 타입 검사 쪽으로 범위를 줄일 수 있다. 재현되지 않는다면 라이브러리 시그니처에서 추가 조건을 찾아야 한다.

## 8. extends로 제한하면 추가 속성도 금지될까?

제네릭에서 자주 보는 `T extends Reply`도 별개의 계약이다. 이 표현은 `T`가 `Reply`의 조건을 만족하도록 제한한다. 두 타입의 키 집합이 같아야 한다는 뜻은 아니다.

```ts
type Reply = { id: string };

function keep<T extends Reply>(value: T): T {
  return value;
}

const kept = keep({ id: "p1", debug: true });
console.log(kept.debug); // true
```

이 호출에서 `T`는 `Reply` 하나로 고정되지 않는다. `id`와 `debug`를 가진 객체 타입으로 추론될 수 있고, 그 타입은 `Reply`를 만족한다. 반환 타입도 `T`라서 `debug` 정보가 유지된다.

이것은 잘못된 동작이 아니라 이런 함수를 작성하는 이유가 될 수 있다. 최소한 `id`가 필요하지만 호출자가 가진 추가 정보는 보존하고 싶을 때 유용하다. 반대로 “id 이외의 키가 들어오면 오류”가 목적이라면 `extends Reply`만으로는 그 계약을 표현하지 못한다.

타입 인자를 직접 `Reply`로 지정하는 호출과, 제약 아래에서 더 구체적인 `T`를 추론하는 호출도 구분해야 한다. 제네릭이 있다는 사실만으로 항상 추가 속성이 허용되거나 항상 금지되는 것은 아니다. 타입 인자를 어떻게 결정했고 그 타입을 어디에 사용했는지가 중요하다.

이 지점에서 내가 바꾸고 싶은 질문은 “더 강한 제네릭을 어떻게 쓰지?”가 아니다. “이 함수는 추가 정보를 보존해야 하나, 필요한 정보만 노출해야 하나, 아니면 추가 정보 자체를 거절해야 하나?”다. 원하는 관계가 먼저 정해져야 문법 선택도 의미가 생긴다.

## 9. 타입 표기, as, satisfies는 서로 바꿔 쓸 수 있을까?

객체 옆에 타입 이름을 적을 수 있는 문법이 여러 개라서 혼동하기 쉽다. 같은 값으로 세 가지를 비교해 보자.

```ts
type Reply = { id: string };

const source = { id: "p1", debug: true };

const annotated: Reply = source;
const asserted = source as Reply;
const checked = source satisfies Reply;

// @ts-expect-error: annotated는 Reply로 선언했다
annotated.debug;
// @ts-expect-error: asserted 표현식은 Reply로 단언했다
asserted.debug;
checked.debug; // 통과
```

타입 표기인 `: Reply`는 변수에 사용할 타입을 선언한다. 대입하는 값이 그 타입과 호환되는지도 검사한다. `as Reply`는 그 표현식을 `Reply`로 취급하도록 단언한다. 단언에는 허용되는 범위가 있지만, 실제 데이터 검사나 변환을 수행하지는 않는다.

`satisfies Reply`는 표현식이 `Reply`에 맞는지 확인한다. 위 예제에서는 `source`가 가진 구체적인 속성 정보를 유지하기 때문에 `checked.debug`에도 접근할 수 있다. `checked`를 `Reply`로 선언한 것과 결과가 다르다. [satisfies 도입 문서](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator)

중요한 점은 세 문법 모두 `source`에서 `debug`를 지우지 않는다는 것이다. 표현식의 정적 타입을 어떻게 취급하는지와 객체의 속성 집합을 바꾸는 일은 별개다.

특히 객체 리터럴에서 초과 속성 오류가 났을 때 곧바로 `as Reply`를 붙이면, 처음 발견하려던 실수를 가릴 수 있다. 목표가 잘못 적은 필드의 검출이었다면 단언은 그 목표에 맞는 해결책이 아니다. 값의 타입을 더 잘 알고 있어서 단언해야 하는 상황과, 오류를 없애고 싶은 상황을 구분해야 한다.

다만 `satisfies`를 “타입 추론에 어떤 영향도 주지 않는 문법”으로 기억하는 것도 정확하지 않다. 목표 타입이 객체 리터럴의 문맥적 타입 추론에 관여할 수 있다. 모든 상황에서 `satisfies`를 떼었을 때와 추론 결과가 완전히 같다고 보장하는 식으로 이해하지 않는다. 이 글에서 확실히 비교한 것은 위의 기존 변수 예제에서 `debug` 정보가 유지된다는 사실이다.

## 10. satisfies는 객체를 만드는 곳에 붙여야 할까?

새 리터럴에 직접 붙인 경우와 기존 변수에 붙인 경우를 나란히 놓아보자.

```ts
type Reply = { id: string };

// @ts-expect-error: 생성 지점의 추가 속성
const direct = { id: "p1", debug: true } satisfies Reply;

const source = { id: "p1", debug: true };
const indirect = source satisfies Reply; // 통과

console.log(indirect.debug); // true
```

첫 번째는 “지금 이 객체를 `Reply`에 맞춰 작성하고 있다”는 위치에서 검사한다. 두 번째는 이미 있는 `source`가 `Reply`로 쓰일 수 있는지 확인한다. 후자는 `source`의 모든 속성이 `Reply`에 열거되어 있어야 한다는 별도 규칙을 추가하지 않는다.

이 차이 때문에 `satisfies`를 어디에 놓을지는 목적에 따라 달라진다. 응답 객체를 손으로 만들면서 필드 이름을 검증하려면 그 객체를 만드는 표현식에 붙이는 것이 직접적이다. 이미 다른 함수에서 얻은 값을 검증하려고 마지막 줄에 붙인다면 기대했던 추가 키 검사가 일어나지 않을 수 있다.

그렇다고 기존 변수에 붙이는 사용이 무의미한 것은 아니다. 필수 필드나 값의 호환성을 확인하면서 기존 타입 정보를 유지하는 데 의미가 있다. 다만 그 효과를 “객체에 정확히 이 키만 있다”는 보장으로 넓혀서는 안 된다.

함수 안에서 사용할 때도 같은 원칙으로 읽을 수 있다. `return { id: "p1" } satisfies Reply`는 객체 생성 지점에 검사 의도를 드러낸다. `const result = otherFunction(); return result satisfies Reply`는 이미 얻은 값의 호환성을 확인한다. 코드를 검토할 때는 `satisfies`라는 단어가 존재하는지보다 그 왼쪽에 어떤 표현식이 있는지를 봐야 한다.

## 11. spread로 새 객체를 만들면 다시 검사되지 않을까?

`source`는 기존 변수라서 추가 필드가 통과했다. 그렇다면 `{ ...source }`로 새 리터럴을 만들면 모든 필드가 다시 검사될까?

```ts
type Reply = { id: string };
const source = { id: "p1", debug: true };

const spreadReply = { ...source } satisfies Reply;
console.log(spreadReply.debug); // true

// @ts-expect-error: 직접 추가한 trace는 검출한다
const explicitExtra = { ...source, trace: true } satisfies Reply;

const spreadWithAnnotation: Reply = { ...source }; // 통과
console.log(JSON.stringify(spreadWithAnnotation));
// {"id":"p1","debug":true}
```

이 예제에서는 spread로 들어온 `debug`와 직접 작성한 `trace`가 다르게 취급된다. 겉으로 객체 리터럴이 보인다는 이유만으로 펼쳐 넣은 키까지 모두 금지된다고 생각하면 안 된다.

JavaScript의 실행 관점에서도 spread는 필요한 속성만 고르는 문법이 아니다. 이 평범한 객체에서는 `source`의 열거 가능한 자체 속성을 새 객체로 복사한다. 그러므로 `debug`를 가지고 있는 객체를 펼치면 새 객체에도 그 속성이 생긴다.

이 차이는 응답 객체를 만들 때 쉽게 나타날 수 있다. `return { ...row } satisfies Reply`라고 작성하면 타입에 맞는 응답을 만들었다는 느낌이 든다. 하지만 `row`가 가진 추가 필드도 복사된다. 타입 검사가 성공한 사실만으로 응답 속성 목록을 제한했다고 볼 수 없다.

반대로 필요한 필드만 직접 적으면 무엇을 보내는지가 코드에 드러난다. `return { id: row.id }`와 `return { ...row }`의 차이는 취향이 아니라 실제 만들어지는 객체의 차이다. 응답에 포함할 필드를 제어하려는 상황에서는 이 차이가 핵심이다.

spread가 항상 나쁘다는 뜻은 아니다. 설정을 합치거나 내부 데이터를 복사하는 데 유용하다. 다만 “복사”와 “선택”은 다른 작업이고, 타입 표기를 붙였다고 복사가 선택으로 바뀌지는 않는다.

## 12. 타입 유틸리티로 키를 제한하면 해결될까?

추가 키를 정적으로 검사하고 싶어서 `keyof`, `Exclude`, `never`를 조합할 수도 있다. 원리를 보기 위한 작은 예제를 만들어 보자.

```ts
type Reply = { id: string };

type NoExtra<Actual, Shape> = Actual &
  Record<Exclude<keyof Actual, keyof Shape>, never>;

function acceptExact<T extends Reply>(value: NoExtra<T, Reply>): T {
  return value;
}

acceptExact({ id: "p1" }); // 통과

const source = { id: "p1", debug: true };
// @ts-expect-error: 이 호출에서 debug는 never여야 하므로 거절된다
acceptExact(source);

const narrowed: Reply = source;
acceptExact(narrowed); // 통과
```

이 유틸리티는 `Actual`에 있지만 `Shape`에는 없는 키를 구한다. 그 키들의 값 타입을 `never`로 요구해, 추가 키가 있는 값을 그대로 전달하기 어렵게 만든다. `source`의 타입에는 `debug`가 보이므로 여기서는 오류가 난다.

하지만 마지막 호출은 통과한다. `narrowed`의 정적 타입은 이미 `Reply`이고, 그 타입의 `keyof`에는 `debug`가 없다. 실제 객체가 가진 모든 키를 타입 시스템이 다시 조회하는 것이 아니다. 유틸리티가 보는 것은 전달된 표현식에 남아 있는 타입 정보다.

이 예제를 완성된 범용 `Exact` 구현으로 가져다 쓰기보다는, 정적 검사의 범위를 보여주는 실험으로 읽는 편이 좋다. 중첩 객체, 유니언, 인덱스 시그니처, 제네릭 추론, 명시적 타입 인자에 따라 별도 검토가 필요하다. 한 단계의 키를 비교했다고 객체 내부까지 재귀적으로 같은 모양이 되는 것도 아니다.

정확한 키 검사가 API 설계에 도움이 되는 경우는 있다. 그러나 타입 유틸리티를 정교하게 만들수록 컴파일 오류의 가독성과 추론의 편의성도 함께 살펴야 한다. 무엇보다 외부 JSON을 실제로 검사하는 코드를 대신하지 못한다는 제한은 그대로 남는다.

여기서 런타임 검사로 넘어가는 이유가 보인다. 컴파일러가 알고 있는 타입 정보의 범위 안에서 추가 키를 검출하는 일과, 실행 중 받은 객체의 키를 직접 살펴보는 일은 다른 작업이다.

## 13. 타입을 지운 JavaScript에서 무엇이 남는가?

TypeScript를 컴파일한 뒤에는 타입 표기와 `satisfies` 같은 타입 검사 문법이 런타임 검증기로 남지 않는다. 다음 예제를 보자.

```ts
type Reply = { id: string };

const source = { id: "p1", debug: true };
const reply: Reply = source;
const checked = source satisfies Reply;

console.log(JSON.stringify(reply));
console.log(JSON.stringify(checked));
// 둘 다 {"id":"p1","debug":true}
```

여기서 타입 관련 부분을 제외하고 보면 핵심은 `const reply = source`와 `const checked = source`다. 속성을 삭제하거나 별도의 검증 함수를 호출하는 코드가 없다. 그래서 직렬화할 때도 `debug`가 남는다. [TypeScript 타입의 제거](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types)

이 실험에서 JSON 직렬화가 TypeScript 타입을 읽어서 속성을 고르는 것은 아니다. 실제 JavaScript 객체를 직렬화한다. 여기서는 단순한 문자열·불리언 속성을 가진 객체라 결과도 단순하지만, 실제 직렬화에는 `undefined`, `toJSON`, 열거 가능 여부 등 JavaScript 규칙이 영향을 준다. 그 전체 규칙을 추가 키 검사와 혼합하지는 않겠다.

필드를 선택하려면 실제 선택 코드를 작성할 수 있다.

```ts
type Reply = { id: string };

function toReply(value: Reply): Reply {
  return { id: value.id };
}

const source = { id: "p1", debug: true };
console.log(JSON.stringify(toReply(source))); // {"id":"p1"}
console.log(JSON.stringify(source)); // {"id":"p1","debug":true}
```

`debug`가 사라진 대상은 새로 만든 반환 객체다. 원본을 수정한 것은 아니다. 이 구분은 뒤에서 Valibot의 파싱 결과를 사용할 때도 중요해진다.

다만 `toReply`가 `id`를 읽어 새 객체에 넣는다고 해서 문자열 검증까지 하는 것은 아니다. TypeScript 내부에서 신뢰할 수 있는 `Reply`를 받아 응답을 구성하는 함수다. 외부 입력을 `as Reply`로 단언한 다음 여기에 넣으면, 잘못된 값도 그대로 복사할 수 있다. 필드 선택과 값 검증 역시 서로 다른 책임이다.

## 14. 외부에서 받은 값은 unknown으로 시작한다

서버 응답, 요청 본문, 저장된 JSON은 TypeScript 코드 바깥에서 들어올 수 있다. 이런 값이 실제로 어떤 모양인지는 타입 이름을 붙인 것만으로 확인되지 않는다.

```ts
type Reply = { id: string };

const raw: unknown = JSON.parse('{"id":123,"debug":true}');

// @ts-expect-error: unknown을 바로 Reply로 사용할 수 없다
const unchecked: Reply = raw;

const asserted = raw as Reply;
console.log(typeof asserted.id); // number
```

`as Reply` 뒤에서 편집기는 `id`를 문자열로 다루도록 허용할 수 있다. 하지만 실행 결과는 숫자다. 단언은 데이터의 자료형을 바꾸지 않았고, `JSON.parse`가 성공했다는 사실도 우리가 원하는 객체 구조를 보장하지 않는다. 유효한 JSON 문법과 유효한 업무 데이터는 다르다.

`unknown`은 이 차이를 코드에 남겨두는 데 도움이 된다. 값을 받았다는 사실은 인정하되, 검사하기 전에는 특정 속성을 가진 타입이라고 가정하지 않도록 만든다. 직접 타입 가드를 작성할 수도 있고 스키마 라이브러리로 구조를 검사할 수도 있다.

이 글에서는 추가 필드에 대한 정책을 비교하기 위해 Valibot을 사용한다. 라이브러리를 도입하는 이유를 “타입을 더 엄격하게 한다” 정도로만 설명하면 다시 혼동하기 쉽다. 여기서는 실제 입력을 읽고, 필드 값을 검사하고, 출력 객체를 구성하거나 검증 실패를 알려주는 실행 코드가 필요하다.

그 결과를 내부 코드에서 어떤 타입으로 다룰지는 또 다른 단계다. 스키마에서 타입을 추론하면 두 단계를 연결할 수 있지만, 타입을 추론한 것만으로 파싱을 실행한 것은 아니다.

## 15. 같은 입력으로 Valibot의 네 가지 객체 스키마 비교하기

먼저 선택지를 한눈에 놓고 보자. 입력에 스키마가 선언하지 않은 평범한 추가 속성이 있을 때의 차이다.

| 스키마 | 추가 속성에 대한 기본 정책 | 성공한 출력에서의 처리 |
| --- | --- | --- |
| `object` | 선언한 속성을 검사 | 선언하지 않은 속성 제외 |
| `strictObject` | 선언하지 않은 속성을 오류로 처리 | 추가 속성이 있으면 성공하지 않음 |
| `looseObject` | 추가 속성을 허용 | 추가 속성 보존 |
| `objectWithRest` | 추가 속성에도 별도의 스키마 적용 | 검사를 통과한 추가 속성 포함 |

이 정책들은 TypeScript가 리터럴을 직접 보았는지와 무관하게 실행된다. `unknown` 값으로 들어왔든, 변수에 담겨 있었든, 파서가 실행되면 입력을 실제로 검사한다. 아래 비교는 일반적인 JSON 형태의 객체를 대상으로 한다. `looseObject`와 `objectWithRest`는 보안상 일부 키를 필터링하므로, 모든 JavaScript 객체의 모든 키를 무조건 복제한다는 뜻으로 일반화하지 않는다. [Valibot 객체 가이드](https://valibot.dev/guides/objects/)

### object: 추가 필드를 출력에서 빼기

```ts
import * as v from "valibot";

const ReplySchema = v.object({
  id: v.string(),
});

const input = { id: "p1", debug: true };
const output = v.parse(ReplySchema, input);

console.log(JSON.stringify(output)); // {"id":"p1"}
console.log(JSON.stringify(input)); // {"id":"p1","debug":true}
console.log(output === input); // false
```

이 결과에서 `debug`가 빠지는 것은 `Reply`라는 TypeScript 타입을 적어서가 아니다. `v.parse`가 `object` 스키마를 실행했고, 선언된 속성에 맞는 출력 객체를 만들었기 때문이다. [object API](https://valibot.dev/api/object/)

여기서 원본 `input`은 그대로라는 점을 눈여겨보자. 파싱한 결과가 필요한 코드라면 `output`을 사용해야 한다. 다음처럼 파싱만 호출하고 원본을 반환하면 이 예제에서 의도한 필드 제거 효과를 받지 못한다.

```ts
import * as v from "valibot";

const ReplySchema = v.object({ id: v.string() });

function parseButReturnOriginal(input: unknown): unknown {
  v.parse(ReplySchema, input);
  return input;
}

function returnParsed(input: unknown) {
  return v.parse(ReplySchema, input);
}

const input = { id: "p1", debug: true };
console.log(JSON.stringify(parseButReturnOriginal(input)));
// {"id":"p1","debug":true}
console.log(JSON.stringify(returnParsed(input)));
// {"id":"p1"}
```

이것은 실제 사용 코드에서 확인할 가치가 있는 차이다. 검증 함수를 호출했다는 사실만 검색하면 두 함수 모두 비슷하게 보일 수 있다. 하지만 이후에 어떤 값을 전달하는지가 다르다. 검증, 변환, 기본값 적용이 있는 스키마라면 더욱 파싱 결과를 사용하는지 확인해야 한다.

`object`는 추가 필드를 거절하는 정책도 아니다. `debug`가 있는 입력을 허용한 뒤 출력에서 제외했다. API 계약상 알 수 없는 필드 자체를 오류로 알려야 한다면 다른 선택이 필요하다.

### strictObject: 추가 필드가 있다는 사실을 오류로 처리하기

```ts
import * as v from "valibot";

const ReplySchema = v.strictObject({
  id: v.string(),
});

const result = v.safeParse(ReplySchema, {
  id: "p1",
  debug: true,
});

console.log(result.success); // false
if (!result.success) {
  console.log(result.issues.length); // 이 입력에서는 1
}
```

`strictObject`는 이 입력을 성공으로 받아들이지 않는다. `debug`를 버리고 계속 진행하는 대신, 선언하지 않은 속성이 들어왔다는 사실을 검증 실패로 드러낸다. [strictObject API](https://valibot.dev/api/strictObject/)

여기서는 `safeParse`를 사용했으므로 결과의 `success`를 확인할 수 있다. `parse`는 검증 실패를 예외로 전달하고, `safeParse`는 성공 여부와 결과를 담은 값을 반환한다. 어느 쪽을 선택하든 실패한 값을 정상 결과처럼 사용하지 않는 흐름을 작성해야 한다.

오타를 사용자에게 알려야 하는 입력이라면 이런 정책이 유용할 수 있다. 예를 들어 수정 API에서 `displayName` 대신 `displayNmae`를 보냈는데 조용히 버리면, 호출자는 요청이 성공했는데 왜 값이 바뀌지 않는지 알기 어렵다. 추가 필드를 오류로 처리하면 이 차이를 드러낼 수 있다.

반면 확장 필드를 보낼 수 있는 클라이언트와 하위 버전 서버가 함께 동작해야 한다면, 알 수 없는 모든 필드를 거부하는 정책이 호환성에 영향을 줄 수 있다. `strictObject`라는 이름이 더 안전해 보인다는 이유만으로 모든 경계에 적용하기보다는, 그 경계에서 추가 필드를 어떤 의미로 볼지 정해야 한다.

또한 이 스키마는 모든 알 수 없는 키에 대한 오류를 끝없이 모으는 방식이 아니다. 공식 문서는 알 수 없는 속성에 대해 하나의 이슈를 반환하도록 설계했다고 설명한다. “이슈가 하나니까 추가 키도 정확히 하나였다”라고 역으로 추론하지는 않는다.

### looseObject: 추가 필드를 남겨두기

```ts
import * as v from "valibot";

const ReplySchema = v.looseObject({
  id: v.string(),
});

const output = v.parse(ReplySchema, {
  id: "p1",
  debug: true,
});

console.log(JSON.stringify(output)); // {"id":"p1","debug":true}
```

이 경우 `id`는 문자열인지 검사하지만, 예제의 추가 속성 `debug`는 출력에 남는다. 일부 정해진 필드는 알고 있고 나머지 확장 정보를 보존해야 하는 데이터에서 생각해 볼 수 있는 정책이다. [looseObject API](https://valibot.dev/api/looseObject/)

하지만 보존했다는 사실과 그 값의 업무적 의미를 검사했다는 사실은 다르다. `debug`를 스키마에 선언한 것이 아니므로 `id`와 같은 방식으로 불리언 검사를 한 것은 아니다. 다음 코드에서 추가 속성을 실제로 사용할 때는 그 값에 대해 무엇을 알고 있는지 따로 확인해야 한다.

특히 “전체 입력을 잃지 않고 기록하고 싶다”와 “외부로 공개해도 되는 속성만 내보내고 싶다”는 반대 방향의 요구일 수 있다. 두 경우에 같은 스키마를 재사용하면 편하지만, 정책이 정말 같은지 먼저 확인해야 한다.

### objectWithRest: 추가 필드의 값에도 조건을 주기

```ts
import * as v from "valibot";

const ReplySchema = v.objectWithRest(
  { id: v.string() },
  v.boolean(),
);

const accepted = v.safeParse(ReplySchema, {
  id: "p1",
  debug: true,
  preview: false,
});

const rejected = v.safeParse(ReplySchema, {
  id: "p1",
  debug: "yes",
});

console.log(accepted.success); // true
if (accepted.success) {
  console.log(JSON.stringify(accepted.output));
  // {"id":"p1","debug":true,"preview":false}
}
console.log(rejected.success); // false
```

첫 번째 인자는 이름이 정해진 속성에 대한 스키마다. 두 번째 인자는 그 외 속성에 적용할 스키마다. 이 예제의 `id`는 문자열이어야 하고, 나머지 속성은 불리언이어야 한다. 두 번째 스키마가 `id`까지 불리언으로 요구하는 것은 아니다. [objectWithRest API](https://valibot.dev/api/objectWithRest/)

이 방식은 추가 키를 모두 같은 조건으로 다룰 때 유용하다. 다만 추가 키 이름 자체에 복잡한 규칙이 있거나 필드 간 관계가 있다면 별도의 설계가 필요하다. “나머지 값은 불리언”이라는 계약과 “허용된 기능 이름만 키로 쓸 수 있다”는 계약도 같지 않다.

이제 같은 `debug`라는 추가 필드에 대해 네 가지 다른 결정을 할 수 있다. 제거할지, 거절할지, 보존할지, 별도 조건으로 검사할지다. 이 선택은 타입 검사 강도를 한 줄로 올리고 내리는 문제가 아니라 프로그램이 실제 입력을 처리하는 정책이다.

## 16. 바깥 객체를 검사하면 안쪽도 같은 정책일까?

중첩 객체를 만나면 정책을 한 단계 더 구체적으로 정해야 한다. 바깥에서 `strictObject`를 사용했다고 안쪽의 모든 객체까지 자동으로 strict가 되는 것은 아니다.

```ts
import * as v from "valibot";

const EnvelopeSchema = v.strictObject({
  payload: v.object({ id: v.string() }),
});

const nestedExtra = v.safeParse(EnvelopeSchema, {
  payload: { id: "p1", debug: true },
});

const outerExtra = v.safeParse(EnvelopeSchema, {
  payload: { id: "p1" },
  debug: true,
});

console.log(nestedExtra.success); // true
if (nestedExtra.success) {
  console.log(JSON.stringify(nestedExtra.output));
  // {"payload":{"id":"p1"}}
}
console.log(outerExtra.success); // false
```

바깥 객체의 선언된 키는 `payload`뿐이다. 그래서 바깥에 추가한 `debug`는 거절된다. 안쪽의 `payload`에는 `object`를 사용했으므로 그 안의 `debug`는 출력에서 제외된다. 서로 다른 위치에서 서로 다른 정책이 실행된 것이다.

이 점을 놓치면 “엄격한 스키마를 썼는데 왜 안쪽의 추가 필드는 오류가 아니지?”라는 새 혼동이 생긴다. 스키마를 읽을 때는 최상단 함수 이름만 보지 말고, 검사하려는 속성이 어느 객체 스키마 안에 들어 있는지 따라가야 한다.

실제로 이런 혼합이 적절할 수도 있다. 요청 봉투의 형식은 고정하되 내부 메타데이터는 확장 가능하게 설계할 수 있기 때문이다. 중요한 것은 모든 단계에 무조건 같은 정책을 쓰는 것이 아니라, 각 경계에서 허용 범위가 의도대로 정해져 있는지다.

## 17. InferOutput으로 얻은 타입은 파싱했다는 증거일까?

스키마에서 타입을 추론하면 필드 정의를 두 번 적지 않아도 된다. 하지만 `InferOutput`을 사용했다고 런타임 파싱이 실행되지는 않는다.

```ts
import * as v from "valibot";

const ReplySchema = v.object({ id: v.string() });
type Reply = v.InferOutput<typeof ReplySchema>;

const source = { id: "p1", debug: true };
const assigned: Reply = source; // 구조적 호환성으로 통과
const parsed = v.parse(ReplySchema, source);

console.log(JSON.stringify(assigned)); // {"id":"p1","debug":true}
console.log(JSON.stringify(parsed)); // {"id":"p1"}
```

이 예제는 글의 앞부분으로 다시 연결된다. `Reply`가 스키마에서 유래한 타입이어도 TypeScript 타입으로 사용하는 순간에는 정적 호환성 규칙을 따른다. 그 타입의 변수에 대입하는 것과 스키마를 실행해 얻은 출력은 같은 연산이 아니다.

`InferOutput`은 스키마의 출력 타입을 얻는 도구다. `InferInput`은 스키마가 기대하는 입력 타입을 얻는다. 변환이나 기본값을 사용하는 스키마에서는 둘이 달라질 수 있다. 중요한 것은 외부 데이터가 그 타입을 만족한다는 사실을 확인하려면 실제 파싱 단계가 필요하다는 점이다. [Valibot 타입 추론 가이드](https://valibot.dev/guides/infer-types/)

따라서 검증 결과를 내부 코드로 넘길 때는 `safeParse`의 성공 분기에서 `output`을 사용하는 흐름이 분명하다.

```ts
import * as v from "valibot";

const ReplySchema = v.object({ id: v.string() });

function readReply(input: unknown) {
  const result = v.safeParse(ReplySchema, input);
  if (!result.success) {
    return { kind: "invalid" as const, issues: result.issues };
  }
  return { kind: "valid" as const, value: result.output };
}

const result = readReply({ id: "p1", debug: true });
if (result.kind === "valid") {
  console.log(JSON.stringify(result.value)); // {"id":"p1"}
}
```

여기서 호출자가 받는 값은 검사에 성공한 출력이다. 입력을 타입 단언으로 바꿔 넘기지 않았고, 파싱한 다음 원본을 반환하지도 않았다. 실패를 어떻게 전달할지는 서비스의 에러 처리 규칙에 따라 달라질 수 있지만, 성공 경로에서 어떤 데이터를 사용하는지는 명확해야 한다. [safeParse의 결과 사용법](https://valibot.dev/api/safeParse/)

## 18. 실제 코드에서는 무엇부터 바꿀까?

이제 처음 질문으로 돌아갈 수 있다. 타입을 지정했는데 추가 필드가 통과했다면, 먼저 의도한 계약을 문장으로 적어보는 편이 좋겠다.

“내가 지금 작성하는 객체에 오타가 있으면 바로 알려줬으면 한다.” 이런 요구라면 생성 지점의 타입 표기나 `satisfies`를 먼저 고려할 수 있다. 값이 여러 함수를 거친 뒤에 검사하는 것보다, 잘못 적은 곳에 가까운 위치에서 오류를 발견하기 쉽다.

“함수가 반환하는 값에 최소한 이 필드는 있어야 한다.” 이런 요구라면 반환 타입과 구조적 호환성이 자연스럽다. 다른 정보를 더 가진 객체를 받아들여도 계약에 문제가 없는지 확인하면 된다. 추가 필드를 보존하는 제네릭이 필요한 경우도 이 범주에서 따로 판단할 수 있다.

“응답 JSON에는 이 필드들만 보내야 한다.” 이런 요구라면 실제 객체를 만드는 코드가 필요하다. 명시적으로 필드를 선택하거나, 목적에 맞는 스키마를 파싱하고 그 출력을 반환한다. 타입 표기만 보고 응답 필드가 제거됐다고 판단하지 않는다.

“요청에 알 수 없는 필드가 오면 잘못된 요청이라고 알려야 한다.” 이런 요구라면 입력 경계에서 추가 필드를 오류로 만드는 정책이 필요하다. 스키마가 추가 키를 버리는지 거부하는지 확인하고, 실패 결과를 호출자에게 어떻게 전달할지도 함께 정한다.

이 네 문장은 모두 겉으로는 “타입에 없는 필드를 막고 싶다”로 축약될 수 있다. 하지만 작성하는 코드와 실행 결과는 서로 다르다. 그래서 막연히 타입을 더 엄격하게 만든다는 목표보다, 어느 지점에서 어떤 입력을 어떻게 처리할지 설명하는 것이 중요하다.

검토 순서도 정리할 수 있다. 먼저 TypeScript가 해당 표현식에 어떤 타입을 부여했는지 본다. 그다음 대입 대상이나 함수 시그니처를 확인한다. 새 리터럴인지 기존 변수인지, 직접 쓴 속성인지 spread로 들어온 속성인지 구분한다. 마지막으로 실행 코드에 실제 검사나 필드 선택이 존재하는지 본다.

이 과정을 거치면 빨간 줄을 없애는 수정과 계약을 바로잡는 수정을 구분하기 쉬워진다. `as` 하나로 컴파일러를 조용하게 만들 수 있더라도, 그것이 필요한 데이터 정책을 구현한 것인지는 별도의 질문이다.

처음에는 `db.transaction<…>`에서 예상과 다르게 동작한 사례 하나였지만, 결국 내가 혼동한 것은 객체를 바라보는 세 가지 방식이었다. TypeScript가 호환된다고 판단하는 구조, 작성 지점에서 추가로 검사하는 속성, 실행 중 실제로 존재하는 데이터다.

이제 추가 필드가 통과하는 코드를 보면 곧바로 타입 시스템이 놓쳤다고 생각하지는 않을 것 같다. 그 타입이 약속한 범위 안에서는 올바른 동작일 수 있다. 대신 내가 원했던 약속이 최소 구조인지, 작성 실수의 검출인지, 실제 데이터의 제거 또는 거부인지부터 분명히 해보려고 한다.
