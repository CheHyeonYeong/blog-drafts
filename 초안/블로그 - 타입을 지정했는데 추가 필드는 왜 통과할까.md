# 타입을 지정했는데 추가 필드는 왜 통과할까?

> 작성 근거: [[2026-10-20]]의 `db.transaction<…>` 메모와 [[2026-10-26]]의 “타입 오류가 적재적소에 뜨도록 하자”.
> 원래 업무 코드와 DB 라이브러리의 시그니처를 재현한 글은 아니다. 같은 의문을 살펴보기 위한 독립 예제다.
> 검증 환경: TypeScript 5.9.3 / 6.0.3, `strict`, `target: ES2022`.

TypeScript를 쓰면서 제네릭에 반환 타입을 지정하면, 반환하는 객체의 필드도 그 타입에 적힌 것만 허용될 거라고 생각했다. 그런데 `db.transaction<…>`을 쓰다 추가 필드가 통과하는 것을 보고 메모를 남겼다.

“필요한 필드가 있으면 추가 필드가 있어도 호환되는구나.”

그런데 이 설명만으로는 찜찜했다. 어떤 자리에서는 추가 필드에 빨간 줄이 생기기 때문이다. 같은 객체인데 왜 선언 위치를 바꾸면 결과가 달라질까?

## 변수 하나를 거쳤을 뿐인데

응답에 필요한 정보가 `id` 하나라고 하자. 아래 코드 블록들은 순서대로 하나의 파일에 이어서 실행할 수 있다. `@ts-expect-error`는 바로 다음 줄에서 오류가 나야 한다는 검증 표시다. 편집기에서 실제 오류를 보려면 해당 주석을 지우면 된다.

```ts
type Reply = { id: string };

// @ts-expect-error: 직접 작성한 객체 리터럴의 추가 필드
const direct: Reply = { id: "p1", debug: true };

const source = { id: "p1", debug: true };
const indirect: Reply = source; // 통과
```

`indirect`에 들어간 값에도 `debug`가 있다. 타입 검사가 느슨해지는 마법의 변수라서 통과한 걸까?

두 번째 대입은 구조적 호환성으로 설명할 수 있다. `source`에는 `Reply`가 요구하는 `id: string`이 있다. 추가 필드가 있다고 해서 `id`를 사용하는 데 문제가 생기지는 않는다. 여기서 `Reply`는 객체의 모든 키를 열거한 봉인된 스키마가 아니다. [TypeScript 타입 호환성](https://www.typescriptlang.org/docs/handbook/type-compatibility.html)

첫 번째 대입에는 추가로 **초과 속성 검사(excess property checking)**가 적용된다. 객체 리터럴을 목표 타입에 맞춰 직접 작성하는 자리에서는 잘못 적은 속성을 발견하도록 더 엄격하게 검사한다. 따라서 일반적인 구조적 호환성과 이 검사를 구분해야 한다. [객체 리터럴의 초과 속성 검사](https://www.typescriptlang.org/docs/handbook/2/objects.html#excess-property-checks)

“추가 필드는 항상 허용된다”도, “타입에 없는 필드는 항상 오류다”도 이 두 예제를 함께 설명하지 못한다.

## 제네릭으로 반환 타입을 지정한 경우

DB를 빼고 콜백 결과를 그대로 반환하는 함수를 만들어 보자.

```ts
function run<T>(work: () => T): T {
  return work();
}

const result = run<Reply>(() => ({ id: "p1", debug: true }));

// @ts-expect-error: id의 타입 불일치는 검출한다
run<Reply>(() => ({ id: 123 }));

// @ts-expect-error: 필수 필드 누락도 검출한다
run<Reply>(() => ({ debug: true }));
```

첫 호출은 통과한다. 이 시그니처에서 콜백이 반환하는 `{ id: string; debug: boolean }`은 `Reply`와 호환된다. 타입 인자를 직접 적었다고 반환 객체의 키 집합까지 같아야 한다는 계약이 생기지는 않는다.

그렇다고 제네릭이 검사를 아예 하지 않는 것도 아니다. 숫자 `id`나 필수 필드 누락은 여전히 오류다. 문제는 검사 유무보다 **무엇을 보장하느냐**에 있다.

콜백 자체에 반환 타입을 적고 리터럴을 직접 반환하면 결과가 달라진다.

```ts
run<Reply>((): Reply => {
  // @ts-expect-error: 명시한 반환 타입에 대한 초과 속성 검사
  return { id: "p1", debug: true };
});

run<Reply>((): Reply => source); // 기존 변수 반환은 통과
```

반환 타입 표기도 모든 반환값을 정확한 키 집합으로 제한하지는 않는다. 위의 두 줄을 함께 기억해야 “앞으로 콜백에 타입만 붙이면 해결”이라는 결론을 피할 수 있다.

실제 `db.transaction`에 이 설명을 적용하려면 사용하는 버전의 오버로드와 콜백 시그니처를 확인해야 한다. 여기서는 `run<T>(work: () => T): T`의 동작만 검증했다.

## satisfies도 붙이는 위치가 중요하다

객체를 만드는 자리에서 의도를 확인하고 싶다면 `satisfies`를 사용할 수 있다.

```ts
// @ts-expect-error: 생성하는 자리에서 debug를 검출한다
const checkedLiteral = { id: "p1", debug: true } satisfies Reply;

const checkedVariable = source satisfies Reply; // 통과
checkedVariable.debug; // 이 속성도 그대로 접근 가능
```

`satisfies`는 표현식이 목표 타입과 호환되는지 확인하면서 표현식의 타입 정보를 활용할 수 있게 한다. 변수 자체를 목표 타입으로 선언하는 것과는 다르다. [TypeScript 4.9의 satisfies 설명](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator)

하지만 이미 만들어진 `source`를 검사한다고 객체 리터럴을 새로 작성한 자리가 되지는 않는다. 추가 필드를 가진 변수에도 `satisfies`만 붙이면 정확한 객체가 된다는 기대는 틀렸다.

객체를 펼쳐 새 리터럴을 만들면 어떨까?

```ts
const spreadReply = { ...source } satisfies Reply; // 통과
spreadReply.debug; // 여전히 존재

// @ts-expect-error: 직접 적은 추가 속성은 검사된다
const explicitExtra = { ...source, trace: true } satisfies Reply;
```

이 예제에서 펼치기로 들어온 `debug`와 직접 적은 `trace`는 같은 방식으로 검사되지 않는다. “리터럴에 `satisfies`를 붙였다”는 사실만으로 펼쳐 온 필드까지 제거되거나 금지되지는 않는다.

여기까지 비교하면 다음과 같다. 표는 위의 `Reply` 예제에 대한 결과다.

| 작성 방식 | 추가 필드 결과 |
| --- | --- |
| `const x: Reply = { id, debug }` | 오류 |
| 기존 변수를 `Reply`에 대입 | 통과 |
| `run<Reply>(() => ({ id, debug }))` | 통과 |
| `(): Reply => ({ id, debug })` | 오류 |
| `{ id, debug } satisfies Reply` | 오류 |
| 기존 변수에 `satisfies Reply` | 통과 |
| `{ ...source } satisfies Reply` | 통과 |

## 타입에 안 보이는 필드도 JSON에는 남는다

이 차이는 편집기의 자동완성으로 끝나지 않는다.

```ts
// @ts-expect-error: result의 정적 타입에는 debug가 없다
result.debug;

console.log(JSON.stringify(result));
// {"id":"p1","debug":true}
```

`result`의 정적 타입은 `Reply`다. 하지만 `run`은 원래 객체를 그대로 반환한다. 타입을 작게 보이게 했다고 실제 객체에서 속성을 삭제하지는 않았다. 이 코드를 실행하면 `debug`도 직렬화된다.

응답 필드를 제한하려는 목적이라면, 타입 표기와 실제 응답 객체 구성을 따로 생각해야 한다. 이 예제에서는 필요한 필드를 직접 선택할 수 있다.

```ts
function toReply(value: Reply): Reply {
  return { id: value.id };
}

console.log(JSON.stringify(toReply(source)));
// {"id":"p1"}
```

여기서 `debug`가 빠진 이유는 반환 타입 때문이 아니라 함수 본문에서 `id`만 새 객체에 담았기 때문이다. 단, 이 함수는 이미 타입을 신뢰할 수 있는 내부 값을 받는 예제다. 외부 JSON의 `id`가 문자열인지 검사하는 런타임 검증까지 대신하지는 않는다.

## 이제는 오류를 발견할 자리를 먼저 고른다

원래 메모는 “제네릭을 적었는데 추가 필드를 못 잡는다”였다. 예제를 나눠 보니 기대했던 계약을 더 정확히 말할 수 있게 됐다.

객체를 직접 작성하며 오타나 불필요한 속성을 잡으려면 그 생성 지점에 타입 표기나 `satisfies`를 둔다. 기존 객체를 받아 필요한 필드를 사용하려면 구조적 호환성이 자연스럽다. 실제 응답에서 필드를 제외하려면 반환 객체를 명시적으로 구성한다.

이 세 가지를 모두 “타입을 엄격하게 적는다”로 묶어 생각했던 것이 혼동의 시작이었다. 다음에 빨간 줄이 기대한 곳에 나타나지 않으면, 먼저 그 자리가 새 객체를 검사하는 곳인지, 이미 있는 값의 호환성을 확인하는 곳인지 살펴보려고 한다.
