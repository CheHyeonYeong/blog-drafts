# 타입에 없는 필드인데, 변수에 담으면 왜 통과할까?

요즘 TypeScript를 쓰면서 내가 타입을 생각보다 대충 알고 있었구나 싶을 때가 있다.
타입 적어놨으니까 알아서 잡아주겠지 했는데 안 잡아준다. (물론 내가 잘못 알고 있는 경우가 대부분이긴 하다)

함수에서 받을 결과의 타입을 정해놨는데, 반환되는 객체에 정의되지 않은 필드가 더 있어도 에러가 안 났다.
나는 자바를 많이 써서 그런지 타입을 지정하면 거기에 적힌 필드만 허용되는 줄 알았다. 자바가 모든 추가 필드를 막아준다는 뜻은 아니고, 내가 객체 타입을 그렇게 생각하고 있었다는 얘기다.

필수 필드를 빼면 에러가 난다. 자료형을 틀려도 에러가 난다.
근데 필드를 더 넣는 건 되는 게 신기했다.

찾아보니 필요한 필드가 있으면 추가 필드가 있어도 호환되는 타입으로 본다고 한다.
아 그렇구나 하고 넘어가려는데, 객체를 직접 넣으면 또 에러가 난다. 변수에 담았다가 넣으면 된다.

방금 이해한 것 같은데 아닌가 보다.. 그래서 이 차이부터 정리해봤다.

## 변수에 담았을 뿐인데 왜 봐주지?

복잡한 코드는 빼고 `id` 하나만 있는 타입으로 보자.

```ts
type Reply = { id: string };

// @ts-expect-error: Reply에 없는 debug를 직접 작성했다
const direct: Reply = { id: "p1", debug: true };

const source = { id: "p1", debug: true };
const indirect: Reply = source; // 통과
```

두 객체에 들어 있는 필드는 똑같다. `id`도 있고 `debug`도 있다.
그런데 위쪽은 오류고 아래쪽은 통과한다. 변수에 한번 넣었다고 갑자기 괜찮아지는 게 좀 이상하다.

여기에는 두 가지 검사가 섞여 있다. 먼저 **이 값을 `Reply`로 사용할 수 있는지** 보는 구조적 호환성 검사다.

`Reply`를 받는 코드가 필요한 것은 문자열 `id`다. `source`에는 그게 있다. `debug`가 더 있다고 `id`를 읽지 못하는 것은 아니니, `Reply`를 요구하는 자리에 전달할 수 있다. [TypeScript 타입 호환성](https://www.typescriptlang.org/docs/handbook/type-compatibility.html)

나는 `Reply`를 “이 필드만 있어야 한다”로 읽었는데, 이 상황에서는 “적어도 이 필드는 있어야 한다”에 가깝다.

그렇다고 변수를 거치면 아무 값이나 통과하는 건 아니다. `id`가 숫자이거나 아예 없으면 여전히 오류다. 추가 필드를 허용하는 것과 필요한 필드의 검사를 생략하는 것은 다르다.

그럼 위쪽의 `direct`는 왜 잡힐까?

새 객체 리터럴을 특정 타입에 맞춰 직접 작성하는 자리에는 **초과 속성 검사(excess property checking)**가 추가로 적용된다. 여기서는 `Reply`에 적혀 있지 않은 `debug`를 발견한다. [초과 속성 검사](https://www.typescriptlang.org/docs/handbook/2/objects.html#excess-property-checks)

이 검사는 객체를 직접 쓸 때 생기는 실수를 잡는 데 도움이 된다. 예를 들어 옵션에 `timeout`을 적으려다 `timeuot`이라고 썼는데, 추가 필드도 괜찮다고 넘어가면 오타를 놓치기 쉽다.

그래서 처음 코드의 차이는 이렇게 읽으면 된다.

- `direct`: 지금 `Reply`에 맞춰 객체를 직접 쓰고 있으니, 모르는 필드도 확인한다.
- `indirect`: 이미 있는 `source`를 `Reply`로 사용할 수 있는지 본다. 문자열 `id`가 있으니 통과한다.

변수에 넣어서 모든 타입 검사를 피한 것은 아니다. **새 리터럴에 적용되던 추가 검사가 같은 방식으로 적용되지 않은 것**이다.

## 그럼 잘못 넣은 필드는 어디서 잡아야 할까?

내가 객체를 작성하면서 실수한 필드를 잡고 싶다면, 객체를 만드는 자리에 검사 의도를 적는 게 낫다. 타입 표기를 사용할 수도 있고 `satisfies`를 사용할 수도 있다.

```ts
type Reply = { id: string };

// @ts-expect-error: 생성 지점에서 debug를 검출한다
const direct = { id: "p1", debug: true } satisfies Reply;

const source = { id: "p1", debug: true };
const indirect = source satisfies Reply; // 통과
```

`satisfies`는 표현식이 목표 타입과 호환되는지 확인한다. 위쪽처럼 리터럴에 직접 붙이면 추가 속성도 잡는다. 하지만 아래쪽처럼 이미 있는 변수에 붙인다고 정확히 같은 키만 가진 객체인지 검사해주는 것은 아니다. [satisfies 설명](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator)

이름이 `satisfies`라서 내가 원하는 조건을 다 만족시켜줄 것 같지만, 내가 속으로 생각한 조건까지 검사하지는 않는다.

## 타입에 안 보이는 것과 실제로 없는 것은 다르다

그런데 응답에 `debug`를 보내지 않는 게 목적이라면 타입 검사만으로 끝나지 않는다.

```ts
type Reply = { id: string };

const source = { id: "p1", debug: true };
const reply: Reply = source;

console.log(JSON.stringify(reply));
// {"id":"p1","debug":true}
```

`reply`의 타입에는 `debug`가 안 보인다. 그런데 JSON에는 나온다.

`const reply: Reply = source`에는 속성을 삭제하는 코드가 없다. 같은 객체를 `Reply`라는 타입으로 다룰 뿐이다. 자동완성에서 안 보인다고 실제 객체에서도 없어진 건 아니었다.

응답에서 필드를 빼려면 실제로 필요한 필드만 담아야 한다.

```ts
type Reply = { id: string };

function toReply(value: Reply): Reply {
  return { id: value.id };
}

const source = { id: "p1", debug: true };
console.log(JSON.stringify(toReply(source)));
// {"id":"p1"}
```

이번에 `debug`가 빠진 이유는 `: Reply`가 아니라 `{ id: value.id }`다. 새 객체에 `id`만 넣었으니까 그렇다. 원본 `source`에서 속성을 삭제한 것도 아니다.

이 함수는 필드를 선택하는 예제이고, 외부 데이터의 `id`가 진짜 문자열인지 검증하지는 않는다. 외부 입력의 검증이나 추가 필드를 거절하는 정책은 Valibot 같은 런타임 스키마로 따로 다룰 수 있다. 그건 다음 글에서 이어가려고 한다.

처음에는 타입을 지정했는데 왜 안 잡아주냐고 생각했다. 지금 보니 내가 원한 일이 두 개였다.

**작성할 때 잘못 넣은 필드를 발견하는 것. 그리고 실제로 내보내는 객체에서 필드를 빼는 것.**

첫 번째는 객체를 만드는 지점의 타입 검사를 보고, 두 번째는 실제 반환 객체를 만드는 코드를 봐야 한다. 타입을 더 많이 적는다고 두 번째 일까지 자동으로 처리되지는 않는다.

다음에는 변수에 넣었더니 빨간 줄이 사라졌다고 해결했다고 생각하지 말아야겠다. 에러가 없어진 건 맞는데, 내가 원한 결과가 나온 건지는 아직 모르는 거니까.
